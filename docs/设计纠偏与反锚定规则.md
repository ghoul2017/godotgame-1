# 设计纠偏与反锚定规则

## 1. 目的

本文记录设计纠偏时必须执行的反锚定流程。任何主入口、流程、阶段范围、UI 结构、术语命名和验收标准相关修改，都必须遵守本文。

## 2. 源依据链

设计判断按以下顺序取证：

1. `docs/原始设计.txt`
2. `docs/整体策划案.md`
3. 专项设计文档，例如 UI、数据、轨道站、空投、地表系统文档
4. 分步实现文档
5. 当前代码和资源

下层内容与上层内容冲突时，默认下层内容需要重构。代码和资源不能反向证明设计正确。

## 3. 反锚定流程

每次用户指出理解偏差，必须按顺序执行：

1. 找到源依据原文，引用具体文件和行号。
2. 找到偏差首次出现的文档、代码或资源。
3. 区分这是最终流程、当前阶段范围、调试入口还是临时骨架。
4. 删除或重写错误结构，不做同义词替换式修补。
5. 更新遗留问题，记录尚未同步的代码或资源。
6. 用 `rg` 检索旧词、错误入口和新规则关键字。

## 4. 阶段范围规则

- “最终会发生”不等于“当前阶段要完成”。
- 分步文档只能验收该阶段依赖已经满足的内容。
- 后续系统只能在当前阶段作为接口、载荷字段、锁定状态、调试入口或遗留问题出现。
- 如果某个功能依赖多个后续系统，不能把它写入早期阶段的完成标准。

## 5. 入口和流程规则

- 正式主入口只表达继续游戏、新游戏、设置、退出。
- 轨道站是游戏循环内的永久成长层，不是主入口菜单。
- 后续新游戏正式内容不得被提前写入早期阶段验收。
- 调试直达轨道站、地表或回归结算等场景时，必须归入 `DebugLauncher`、启动参数或独立调试配置。
- 任何正式 UI 文档中出现调试直达按钮，都必须删除或移动到调试章节。

## 6. 术语规则

- 核心术语必须来自源依据或用户明确表述。
- 不得为了修复旧错误创造新概念替代旧概念。
- 如果必须新增术语，先写清它与源依据中原词的关系，并说明为什么需要新增。
- 原始设计中的“资源类型”按矿产类道具处理，不建立玩法层面的全局资源池。
- 玩法文档中提到金属、硅、稀土、能源块、废料、合金、电子元件和纯净数据时，默认它们是 `ItemData` 道具栈，必须位于具体容器或地上物中。
- `Resource` 只允许作为 Godot 资产类型或美术/音频资源引用使用；若指玩法经济对象，必须写成道具、矿产、物资、库存或容器。

## 7. 位置化道具和物流硬规则

涉及矿产、道具、库存、建造、生产、运输、UI 展示或结算时，必须先按以下模型审查，不允许用同义词替换绕过结构问题。

- 矿产来源只产出道具，不存玩家资产，不提供可扣除账户。
- 道具权威状态必须是具体位置：地上、单位背包、空投舱、仓库、建筑输入、建筑输出、施工点、火箭货舱或轨道库存。
- 物流订单必须从具体位置取道具，送到具体位置；不能从 UI 汇总、仓库汇总或全局数值取货。
- 建筑确认放置只创建施工点和施工点库存；材料被搬到施工点后才能施工，不能确认时瞬间扣材料。
- 生产建筑只从自身输入库存消耗，只向自身输出库存产出；输出满时阻塞，不绕过输出库存。
- UI 只展示位置和流转状态，可以做只读汇总，但不能展示或维护可直接扣除的全局数值。

如果发现文档或代码出现“全局资源池”“确认放置扣材料”“生产直接从仓库扣料”“建筑模糊库存”“UI 计数参与扣除”，必须重构数据流和状态所有权，不能只改词。

## 8. 验证规则

纠偏完成后至少运行：

```text
rg -n "旧错误词|错误入口|阶段错位词" docs AGENTS.md -S
rg -n "源依据优先|反锚定|阶段范围|正式主入口" AGENTS.md docs -S
git diff --check
```

检索结果中，旧错误词只能出现在禁止项、遗留问题或审计说明中。
