# 遗留问题

本文只记录后续需要解决的遗留问题。流程经验和已写入入口规则的工作方法不列入本文。

## 1. ScenePayload 通用字典保留

- 当前状态：`ScenePayload` 已拆分为导航载荷、远征创建载荷、回归结算载荷，但仍保留 `Data` 通用字典。
- 为什么现在不解决：第一步刚完成 payload 语义拆分，当前代码已经不再依赖 `Data` 传业务字段；立即删除会扩大改动面，需要同步确认所有场景、调试参数和 Godot 序列化路径都没有残留引用。
- 影响：如果后续继续往 `Data` 写业务散字段，会重新削弱 payload 语义边界，导致场景之间隐式耦合。
- 什么时候解决：新增第二个以上真实场景 payload 数据类后，或搜索确认 `Data` 连续一个开发步骤没有被使用时解决。
- 后续处理：新增场景流程时优先创建明确 payload 数据类；确认 `Data` 长期无用途后删除，或仅保留给调试元数据。
- 阻断级别：当前不阻断第一步；后续继续扩展场景 payload 前必须解决。

## 2. 远征创建职责仍在 GameRoot

- 当前状态：首批正式远征状态由 `GameRoot.CreateExpeditionStartPayload()` 创建。
- 为什么现在不解决：第一步目标是运行骨架和流程闭环，尚未开发正式空投配置、轨道库存扣除、角色选择和远征规则；现在拆服务会提前设计未确定的边界。
- 影响：第一步作为流程骨架可接受，但后续空投配置、轨道库存扣除、角色选择接入后，主入口会承担过多玩法职责。
- 什么时候解决：开发“轨道空投配置”或任何会修改初始单位、携带物资、空投坐标、库存扣除的功能时解决。
- 后续处理：开发正式空投配置时，将远征创建迁移到轨道空投模块或独立远征创建服务，`GameRoot` 只负责路由。
- 阻断级别：当前不阻断第一步；开发轨道空投配置时必须解决。

## 3. 字体配置未形成完整加载链路

- 当前状态：`assets/ui/fonts/default_ui_font_config.tres` 已落地，运行时基础主题由 `UiAssets.CreateBaseTheme()` 创建并使用按钮、面板资源。
- 为什么现在不解决：当前阶段还没有确定正式字体资产，强行绑定字体文件会变成临时资源；现有主题已能统一字号和基础皮肤，满足第一步基础 UI 验收。
- 影响：当前使用 Godot 默认字体和主题字号，可以满足第一步基础 UI；后续接入正式字体时仍需补强加载链路。
- 什么时候解决：确定正式字体资源，或开始做轨道站/地表 HUD 的正式视觉统一阶段时解决。
- 后续处理：引入正式字体资源时，建立 `Theme` 或字体资源加载入口，并确认所有主场景继承同一 UI 主题。
- 阻断级别：当前不阻断第一步；接入正式字体或做 UI 统一时必须解决。

## 4. UI 输入隔离需要随新面板扩展

- 当前状态：地表 HUD 的顶部栏、小地图、信息面板、命令区和消息区已注册输入阻塞。
- 为什么现在不解决：第一步只交付基础 HUD 区域，弹窗、建造菜单、库存拖拽等交互还没有真实节点；无法为不存在的面板做最终输入优先级验证。
- 影响：后续新增弹窗、拖拽面板、建造菜单或库存面板时，如果没有接入统一阻塞逻辑，仍可能发生点击 UI 同时触发地表指令。
- 什么时候解决：每次新增可点击、可拖拽、会覆盖地表画面的 UI 面板时同步解决；新增弹窗时必须优先处理。
- 后续处理：新增 UI 面板时统一调用输入阻塞注册逻辑，复杂弹窗应优先于普通 UI 面板消费输入。
- 阻断级别：当前不阻断第一步；新增复杂 UI 面板或弹窗时必须解决。

## 5. 资源导入与运行时加载策略需统一

- 当前状态：首批 SVG 资源通过运行时 SVG 解析加载，避免 headless 未导入资源时加载失败。
- 为什么现在不解决：第一步资源数量少，运行时 SVG 解析能保证命令行和 headless 验证稳定；现在制定完整导入规范会依赖后续美术资源格式和导出策略。
- 影响：后续若混用导入纹理、运行时 SVG、位图资源，可能出现编辑器能显示但 headless 或导出包加载路径不一致。
- 什么时候解决：开始批量引入位图、字体、音频或准备第一次导出包前解决。
- 后续处理：美术资源规模扩大后，制定统一导入规则；验证时同时覆盖编辑器、headless 和导出前资源路径。
- 阻断级别：当前不阻断第一步；批量引入资源或准备导出前必须解决。

## 6. 首批数据定义仍主要由代码注册

- 当前状态：第二步已新增 `ItemData`、`UnitData`、`BuildingData`、`RecipeData`、`SkillData`、`EventData`、`DropPodData` 等结构，并通过 `DataRegistry` 提供首批正式数据；首批资源已按稳定 ID 绑定图标和精灵路径。
- 为什么现在不解决：当前阶段优先建立统一数据结构、库存转移、空投计划、结算和存档校验链路；把全部首批数据迁移为 `.tres` 或外部数据文件会扩大改动面，并需要同步设计编辑器工作流、导入规范和数据校验入口。
- 影响：数据可验证但编辑器可配置性不足，后续扩展大量道具、建筑、配方、事件时，如果继续堆在 `DataRegistry`，会让数据维护、差异审查和美术引用调整变重。
- 什么时候解决：第三步或后续开始批量扩展道具、建筑、配方、事件、交易条目之前解决；如果策划要求非程序人员直接编辑数据，也必须提前解决。
- 后续处理：明确数据资产格式，优先迁移到 `resources/data/` 下的 Godot Resource 或稳定外部数据文件；保留 `DataRegistry` 作为加载、索引、校验和缺失资源报告入口。
- 阻断级别：当前不阻断第二步；批量扩展正式数据前必须解决。

## 7. GameRoot 仍承担数据初始化和流程服务职责

- 当前状态：第二步为了接入数据链路，`GameRoot` 仍负责加载 `DataRegistry`、初始化轨道库存、创建空投计划、创建远征状态、执行调试回归货舱装载和应用回归结算。
- 为什么现在不解决：当前目标是让第二步数据结构和链路先按最终边界跑通；立即拆分服务会牵连轨道空投 UI、地表火箭装载、存档服务和调试入口，容易把还未开发的系统边界提前写死。
- 影响：`GameRoot` 代码会继续膨胀，后续若在其中继续加入交易、研发、生产、火箭建造或存档读写，会让主入口承担玩法服务，增加回归风险。
- 什么时候解决：开发正式空投配置 UI、地表火箭装载/回归、存档读写或轨道交易研发时解决。
- 后续处理：拆出 `ExpeditionCreationService`、`InventoryTransferService`、`ReturnSettlementService`、`SessionBootstrapService` 或同等职责模块；`GameRoot` 只保留初始化、路由和服务调用。
- 阻断级别：当前不阻断第二步；接入第三个以上状态写回系统前必须解决。

## 8. 正式火箭装载和回归链路尚未实现

- 当前状态：第二步已建立火箭货舱库存 ID、回归 payload、实例道具回归、转移记录和正式结算校验；正式流程会拒绝未建成、未确认发射或缺少有效货舱内容的回归。调试路径可通过 debug 标志生成验证货舱数据。
- 为什么现在不解决：火箭建造、装载 UI、超载燃料消耗和发射反馈属于后续火箭系统步骤，不属于第二步统一数据结构的完整玩法范围。
- 影响：正式地表流程中玩家还不能通过真实火箭装载完成回归；当前只能验证数据结构和防伪造边界，不能作为火箭玩法验收。
- 什么时候解决：开发“火箭建造、装载、回归和结算”步骤时解决；如果第三步需要从地表真实带回资源，也必须先接入对应链路。
- 后续处理：实现火箭组装坪状态、货舱装载 UI、可返回单位/实例选择、发射确认和超载反馈；回归 payload 必须只由该链路生成，并复用现有结算校验。
- 阻断级别：当前不阻断第二步；实现正式回归玩法前必须解决。

## 9. 存档服务已有校验但尚未落地读写文件

- 当前状态：第二步新增 `SaveGame` 和 `SaveGameService`，能校验版本、库存、实例引用、空投计划、轮次转移记录、实例所有权和火箭超载标记；但还没有正式保存到磁盘、读档迁移和错误恢复 UI。
- 为什么现在不解决：当前阶段重点是定义存档结构和校验规则，正式读写、迁移和槽位管理会涉及 UI、文件路径、版本升级策略和失败恢复流程。
- 影响：当前会话状态只能运行时存在，不能作为完整存档系统验收；后续读档时仍需补充迁移、兼容和错误展示。
- 什么时候解决：开始做继续游戏、存档槽、读档恢复、死亡/回归后自动保存或版本迁移时解决。
- 后续处理：实现 `SaveGameService` 的序列化、反序列化、版本迁移、备份和恢复报告；读档后必须重新关联 Resource 定义并运行完整校验。
- 阻断级别：当前不阻断第二步；正式存档/读档功能前必须解决。

## 10. Godot 自动生成的 C# 脚本 UID 需要纳入资源管理规则

- 当前状态：新增 C# 脚本后，Godot headless 验证生成了对应 `.cs.uid` 文件，这些文件当前作为未跟踪项目文件出现。
- 为什么现在不解决：本次实现需要保留 Godot 对脚本资源的识别结果，但项目尚未明确 `.uid` 文件的提交策略和审查方式。
- 影响：如果忽略或误删必要 `.uid`，可能影响 Godot 对 C# 脚本资源的稳定识别；如果无规则地提交，也会增加版本差异噪音。
- 什么时候解决：提交第二步实现前，或下一次新增/重命名 C# 脚本前解决。
- 后续处理：确认 Godot 4.6 .NET 项目中 `.cs.uid` 是否应随脚本提交；若应提交，在代码审查中把它们视为脚本资源元数据；若不应提交，统一写入 `.gitignore` 并验证场景脚本实例化不受影响。
- 阻断级别：提交前需要决策；当前不影响编译和 headless 运行。
