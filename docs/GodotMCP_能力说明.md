# GodotMCP 能力说明

本文面向项目 owner，用于说明当前 GodotMCP 能帮你做什么、怎么提需求更有效，以及它的边界。

## 现在能做什么

GodotMCP 已经能连通本机 Godot .NET 和当前项目。它可以让 AI 不只读文件，还能在一定程度上通过 Godot 引擎理解项目。

已验证能力：

- 读取 Godot 版本。
- 读取 `project.godot`。
- 识别当前项目名和主场景。
- 列出项目文件。
- 读取 `.tscn` 场景树。
- 注册到 Codex MCP 配置，名称为 `godot`。

## 适合交给它的任务

- 检查主场景、入口场景、项目设置是否正确。
- 读取某个场景的节点结构，判断 UI 或场景挂载是否符合设计。
- 运行项目并读取 Godot 输出日志。
- 在游戏运行时截图，辅助判断画面是否正常。
- 读取运行时 UI 树、节点树、节点属性。
- 模拟点击、按键、拖拽，用于简单交互验证。
- 对运行中的游戏执行小段调试检查，例如读取当前场景、相机、UI、性能、节点状态。
- 辅助自动化测试，把“人工打开看看”变成可记录的检查步骤。

## 不适合依赖它的任务

- 普通代码搜索和文本阅读：`rg` 更快。
- 大量 C# 编译问题定位：仍以 `dotnet build` 和编译日志为准。
- 复杂玩法正确性判断：需要项目内测试、日志和明确验收标准。
- 长期替代人工审美判断：截图能辅助发现明显问题，但不能自动保证 UI 好看。
- 一直挂全量工具做普通对话：全量 GodotMCP 有 154 个工具，可能让会话变慢。

## 你可以怎么发需求

更有效的说法：

- “用 GodotMCP 读一下主场景和轨道站场景，确认节点结构是否符合文档。”
- “运行项目，截图主菜单和轨道站，检查有没有明显报错和 UI 遮挡。”
- “用运行时节点检查确认背包窗口打开后有哪些 Control 节点。”
- “对这次场景路由改动做 MCP 验证，结果写入文档。”

不够明确的说法：

- “用 MCP 看看。”
- “测一下游戏。”
- “帮我确认都没问题。”

这类需求需要 AI 自己补验收标准，容易测偏；最好指定场景、入口、期望行为和需要留下的证据。

## 为什么以前感觉慢

主要原因不是单个轻量调用慢，而是：

- 全量 GodotMCP 工具太多，工具列表和模型选择成本高。
- 某些操作会启动 Godot headless，天然有冷启动成本。
- 旧 Claude 配置里曾经设置 `DEBUG=true`，会增加日志噪声。
- 如果每个动作都重新启动项目，而不是保持运行时连接，会变慢。

当前已经做的优化：

- 固定 Godot 路径，避免自动探测。
- 使用 `Godot_mono.app` 的真实路径。
- 设置 `DEBUG=false`。
- 记录了性能基准和后续轻量化方向。

## 后续加速选择

推荐保留两档能力：

- `godot`：全量 GodotMCP，适合需要强控制、运行时检查、截图、场景操作时使用。
- `godot-fast`：轻量 MCP，只暴露常用少量工具，适合日常检查和自动化验证。

如果你觉得普通开发对话变慢，可以让 AI 暂时移除全量 `godot`，改成轻量 `godot-fast`。如果进入专门测试或场景调试阶段，再启用全量能力。

## 风险提示

- GodotMCP 有写文件、改场景、改项目设置、运行项目等强权限。
- AI 使用前应先说明影响范围和验证方式。
- 对正式流程、主场景、自动加载、存档和经济系统相关改动，不应只靠 MCP 结果下结论。
- 项目默认运行时代码是 C#，MCP 方便写 GDScript 不代表应该把业务逻辑写成 GDScript。
