# 第二步策划案：统一数据、道具、库存和存档结构

## 1. 目标定位

第二步要建立所有后续系统共用的数据基础。轨道站、空投配置、地表采集、建造生产、单位装备、火箭装载、回归结算、交易研发、角色成长都必须读写同一套道具、库存和存档结构，避免后续出现多个互不兼容的物资或矿产账户。

本阶段完成后，项目应具备以下能力：

```text
定义道具 / 单位 / 建筑 / 配方 / 技能 / 事件 / 空投舱
-> 创建轨道永久库存
-> 创建地表远征临时库存
-> 在单位、仓库、火箭、轨道之间移动道具
-> 记录当前远征和永久成长状态
-> 为回归结算写回轨道层提供稳定数据接口
```

本阶段不是最终数值平衡阶段，但不是临时数值或临时资源阶段。首批正式数据必须按最终 ID、最终分类、最终资源引用和稳定对象语义落地，用于验证数据形态、引用关系、失败处理和完整链路。

## 2. 系统边界

纳入范围：

- 道具、单位、建筑、配方、技能、事件、空投舱的基础数据定义。
- 道具实例和可堆叠物品结构。
- 库存容器、库存移动、容量和重量统计。
- 轨道永久层数据。
- 当前远征层数据。
- 轮次记录数据。
- 存档文件结构和版本字段。
- 数据 ID 规范、加载规则和错误处理。
- 用于验证链路的首批正式数据。

不在本阶段展开具体内容：

- 轨道交易价格平衡。
- 建筑生产链完整数值。
- 单位 AI、战斗行为和寻路。
- 战争迷雾和程序生成地图。
- 火箭建造过程和发射 UI。
- 角色成长曲线和改装树完整数值。

这些系统可以引用本阶段的数据接口，但不在本阶段实现完整玩法。

## 3. 数据设计原则

### 3.1 稳定 ID 优先

运行时、存档和场景 payload 都使用稳定 ID 引用数据，不使用显示名作为逻辑字段。

示例：

```text
item_id: metal
unit_id: service_bot
building_id: assembler_basic
recipe_id: craft_electronic_parts
skill_id: engineering
```

显示名、描述、图标路径、分类文本只作为表现层数据。

### 3.2 定义数据和实例数据分离

定义数据表达“这类东西是什么”，实例数据表达“当前这个东西的状态”。

定义数据：

- `ItemData`：金属、能源块、AI 芯片、枪械、扫描器等道具定义。
- `UnitData`：服务型机器人、轻型运输无人机、重型运输机器人等单位类型定义。
- `BuildingData`：维修站、组装机、仓库、火箭组装坪等建筑定义。

实例数据：

- `ItemStack`：某个库存中有多少个指定道具。
- `ItemInstance`：不可简单堆叠的装备、芯片、改装件、武器或剧情物品。
- `UnitInstance`：某个具体单位、觉醒者或量产机的状态。
- `BuildingInstance`：地表某个具体建筑的状态。

可批量持有的矿产、加工产物和普通物资优先用堆叠结构表达；带耐久、改装、品质、绑定角色、剧情标记的对象使用实例结构表达。

### 3.3 所有矿产和物资都是道具

原始设计中的基础矿产、加工产物、AI 芯片、机器人改装件、武器、工具、单位平台都必须进入道具体系。地表采集、仓库、火箭货舱、轨道库存、交易研发不各自创建独立矿产字段、物资字段或全局资源池。

任何可被采集、搬运、生产、交易、装载或带回的对象都必须满足以下条件之一：

- 作为 `ItemStack` 位于某个 `InventoryContainer`。
- 作为 `ItemInstance` 被某个库存、单位或建筑持有。
- 作为 `GroundItemState` 落在地表，等待被搬运到具体容器。

UI 可以显示汇总，但汇总只用于观察和筛选，不能作为扣除、建造、生产或交易的权威来源。

信用点是轨道经济货币，作为 `OrbitState` 的数值字段保留；如果后续需要实体化交易物，也可以映射为特殊道具，但本阶段不强制。

### 3.4 道具位置是权威状态

所有道具栈和实例道具都必须有明确位置。数量本身不是玩家资产，位置中的道具才是资产。

允许的位置类型：

- `ground`：地表掉落物或物资堆。
- `unit_inventory`：单位背包。
- `drop_pod_cargo`：空投舱货舱。
- `surface_storage`：地表仓库。
- `building_input`：建筑输入库存。
- `building_output`：建筑输出库存。
- `construction_site`：施工点材料库存。
- `rocket_cargo`：火箭货舱。
- `orbit_inventory`：轨道永久库存。

规则：

- UI 可以把多个位置中的同类道具汇总显示，但这个汇总不是可扣除账户。
- 建造、生产、维修、交易、空投和火箭装载都必须从具体位置读写道具。
- 如果一个流程只知道“当前有多少金属”，但不知道金属在哪里，这个流程不得提交。
- 道具位置变化必须通过库存转移、地表拾取、物流订单或结算写回记录表达。

### 3.5 状态写回可追踪

任何从地表写回轨道的内容都要能追踪来源：

- 来自哪次远征。
- 使用哪个随机种子。
- 从哪个库存容器进入火箭货舱。
- 回归后写入哪个轨道库存或角色列表。
- 哪些内容遗留在地表。

这保证后续排查“物资消失”“重复结算”“觉醒者状态丢失”时有数据依据。

## 4. Resource 定义数据

本章中的 `Resource` 指 Godot 的数据资产类型，不是玩法经济里的“资源”。玩法经济对象统一称为道具、矿产、加工产物、物资、库存或容器。

### 4.1 ItemData

`ItemData` 是所有道具的基础定义。

字段建议：

- `id`：稳定道具 ID。
- `display_name`：显示名。
- `category`：道具大类。
- `sub_category`：子分类。
- `description`：描述。
- `icon_path`：图标资源路径。
- `world_sprite_path`：地表掉落或地图表现资源路径，可为空。
- `max_stack`：最大堆叠数量。
- `unit_weight`：单个重量。
- `base_value`：基础价值，用于交易、结算和调试排序。
- `tags`：标签列表。
- `is_unique`：是否唯一。
- `is_quest_item`：是否关键物品。
- `can_discard`：是否允许丢弃。

道具大类：

- `basic_mineral`：基础矿产道具。
- `processed_item`：加工产物道具。
- `data_core`：数据核心和关键数据。
- `ai_chip`：AI 芯片。
- `mod_part`：改装件。
- `weapon`：武器。
- `tool`：工具。
- `unit_platform`：单位平台或量产机机体。
- `building_module`：建筑模块。
- `blueprint`：蓝图或蓝图碎片。
- `consumable`：弹药、能源包等消耗品。

首批正式道具：

- 金属：`metal`
- 硅：`silicon`
- 稀土：`rare_earth`
- 能源块：`energy_cell`
- 废料：`scrap`
- 合金：`alloy`
- 电子元件：`electronic_parts`
- 纯净数据：`clean_data`
- 数据核心：`data_core`
- 通用 AI 芯片：`ai_chip_basic`
- 简易扫描器：`scanner_basic`
- 简易维修工具：`repair_tool_basic`
- 简易实弹枪：`rifle_basic`

### 4.2 UnitData

`UnitData` 表达单位类型定义，不保存某个单位的当前耐久、装备或经验。

字段建议：

- `id`：稳定单位 ID。
- `display_name`：显示名。
- `description`：描述。
- `unit_role`：单位定位。
- `movement_type`：移动方式。
- `base_durability`：基础耐久。
- `base_energy`：基础能源。
- `inventory_capacity`：携带格位或容量。
- `carry_weight_limit`：携带重量上限。
- `equipment_slots`：装备槽。
- `available_commands`：可执行指令。
- `default_behavior_mode`：默认行为模式。
- `is_awakened_capable`：是否可作为觉醒者类型。
- `icon_path`：单位小图标资源路径。
- `portrait_path`：单位头像资源路径。
- `sprite_path`：地表单位精灵资源路径。
- `selection_radius`：选择圈半径。
- `tags`：标签列表。

初期单位类型：

- `dexter`：主角“灵巧”的基础类型，服务型觉醒者。
- `service_bot`：服务型量产机器人。
- `light_cargo_drone`：轻型运输无人机。
- `heavy_cargo_spider`：重型运输机器人。
- `rockbreaker`：矿工觉醒者“碎石”的基础类型。

### 4.3 BuildingData

`BuildingData` 表达地表建筑定义。

字段建议：

- `id`：稳定建筑 ID。
- `display_name`：显示名。
- `description`：描述。
- `footprint`：占地尺寸。
- `build_cost`：建造消耗道具列表。
- `build_time`：建造时间。
- `power_generation`：发电量。
- `power_consumption`：耗电量。
- `storage_capacity`：库存容量。
- `recipe_ids`：可执行配方。
- `function_tags`：建筑功能标签。
- `icon_path`：建筑图标资源路径。
- `sprite_path`：地表建筑精灵资源路径。
- `preview_sprite_path`：建造预览资源路径。
- `construction_sprite_path`：施工状态资源路径。
- `damaged_sprite_path`：受损状态资源路径。
- `requires_blueprint_id`：需要解锁的蓝图 ID，可为空。

基础建筑：

- `repair_station`：维修站。
- `assembler_basic`：基础组装机。
- `solar_panel`：太阳能板。
- `wind_turbine`：风力发电机。
- `battery_bank`：电池组。
- `fluid_tank`：储罐。
- `storage_box`：仓库。
- `wall_basic`：基础围墙。
- `turret_basic`：自动炮塔。
- `rocket_pad`：火箭组装坪。

### 4.4 RecipeData

`RecipeData` 表达生产和转换关系。

字段建议：

- `id`：稳定配方 ID。
- `display_name`：显示名。
- `input_items`：输入道具列表。
- `output_items`：输出道具列表。
- `work_time`：生产时间。
- `power_cost`：生产能耗。
- `required_building_tags`：可执行该配方的建筑标签。
- `required_blueprint_id`：需要解锁的蓝图 ID，可为空。
- `operator_skill_id`：受哪个技能影响，可为空。

首批正式配方：

- 废料回收金属。
- 金属和硅制造电子元件。
- 金属和稀土制造合金。
- 金属、电子元件和能源块制造基础量产机平台。
- 金属、合金、电子元件和能源块制造火箭部件。

### 4.5 SkillData

`SkillData` 表达熟练度技能定义。

字段建议：

- `id`：稳定技能 ID。
- `display_name`：显示名。
- `description`：描述。
- `max_level`：最大等级。
- `experience_thresholds`：等级经验阈值。
- `effect_tags`：影响范围标签。
- `icon_path`：技能图标资源路径。

初始技能：

- `engineering`：工程。
- `shooting`：射击。
- `mining`：挖矿。
- `control`：控制。

### 4.6 EventData

`EventData` 表达随机事件和探索事件定义。

字段建议：

- `id`：稳定事件 ID。
- `display_name`：显示名。
- `description`：描述。
- `trigger_tags`：触发条件标签。
- `weight`：权重。
- `risk_level`：风险等级。
- `reward_tables`：奖励表引用。
- `icon_path`：事件图标资源路径。
- `story_flags_required`：需要的剧情标记。
- `story_flags_set`：触发后写入的剧情标记。

本阶段只建立结构，不实现随机事件调度。

### 4.7 DropPodData

`DropPodData` 表达空投舱类型定义，只保存可复用配置，不保存某一次远征选择。

字段建议：

- `id`：稳定空投舱 ID。
- `display_name`：显示名。
- `description`：描述。
- `weight_limit`：允许携带重量。
- `slot_limit`：允许携带格位。
- `unit_capacity`：允许携带单位数量或单位体积。
- `accepted_tags`：允许携带的道具标签。
- `blocked_tags`：禁止携带的道具标签。
- `icon_path`：空投舱图标资源路径。
- `sprite_path`：空投舱场景表现资源路径。
- `requires_blueprint_id`：需要解锁的蓝图 ID，可为空。

一次空投准备结果使用 `DropPlan` 表达，属于运行状态和存档数据，不作为 Resource 定义。

## 5. 实例数据

### 5.1 ItemStack

`ItemStack` 用于表达可堆叠道具。

字段：

- `item_id`
- `count`

规则：

- `count` 必须大于 0。
- `item_id` 必须能在 `ItemData` 中找到。
- 同一库存中同一 `item_id` 可以合并，除非该道具不允许堆叠。
- 超过 `max_stack` 时由库存容器拆分为多个堆叠或拒绝加入。
- 普通堆叠不依赖长期 `stack_id` 表达所有权；需要追踪来源时由库存转移记录和轮次记录保存转移批次。

### 5.2 ItemInstance

`ItemInstance` 用于表达不可简单堆叠的道具。

适用对象：

- 带耐久的武器和工具。
- 带品质、词条或绑定状态的 AI 芯片。
- 改装件。
- 剧情关键物品。
- 稀有蓝图碎片。

字段建议：

- `instance_id`
- `item_id`
- `durability`
- `quality`
- `bound_unit_instance_id`
- `modifiers`
- `flags`

### 5.3 UnitInstance

`UnitInstance` 表达一个具体单位。

字段建议：

- `unit_instance_id`
- `unit_id`
- `display_name_override`
- `is_awakened`
- `durability`
- `energy`
- `inventory_id`
- `equipment_instance_ids`
- `mod_part_instance_ids`
- `skill_experience`
- `skill_levels`
- `behavior_mode`
- `current_command`
- `story_flags`

规则：

- 量产机 `is_awakened` 为 false，不记录成长经验。
- 觉醒者 `is_awakened` 为 true，记录技能经验、改装和剧情标记。
- 主角“灵巧”和“碎石”必须使用固定角色实例 ID 或稳定角色 ID，避免存档中重复生成。

### 5.4 BuildingInstance

`BuildingInstance` 表达地表某个具体建筑。

字段建议：

- `building_instance_id`
- `building_id`
- `position`
- `rotation`
- `durability`
- `construction_progress`
- `power_state`
- `input_inventory_id`
- `output_inventory_id`
- `active_recipe_id`
- `production_progress`

建筑不拥有一个模糊的“库存”。生产建筑必须至少区分输入库存和输出库存；仓库类建筑可以只暴露 `storage_inventory_id`，但不能让生产配方直接从全局汇总扣除。

### 5.5 ItemLocation

`ItemLocation` 表达某个道具栈或实例道具当前在哪里。它可以作为查询结果，也可以写入订单、转移记录和调试报告。

字段建议：

- `location_type`
- `inventory_id`
- `owner_type`
- `owner_id`
- `ground_item_state_id`
- `construction_site_id`
- `building_instance_id`
- `slot_index`
- `position`

规则：

- `inventory_id` 指向 `InventoryContainer` 时，`location_type` 必须与库存 owner 语义一致。
- 地上物使用 `ground_item_state_id` 和 `position`。
- 施工点材料使用 `construction_site_id` 和对应施工点库存。
- 任何道具同一时间只能被一个位置拥有。
- `ItemLocation` 不能被 UI 自行生成后用于扣除；UI 只能展示由权威状态查询出的结果。

### 5.6 ConstructionSiteState

`ConstructionSiteState` 表达已确认但尚未建成的施工点。建筑不是确认放置时瞬间扣材料，而是先生成施工点，再由物流把材料送到施工点。

字段建议：

- `construction_site_id`
- `building_id`
- `expedition_id`
- `position`
- `rotation`
- `state`
- `required_items`
- `delivered_inventory_id`
- `assigned_unit_instance_ids`
- `construction_progress`
- `required_work`
- `failure_reason`

`state`：

- `planned`
- `waiting_materials`
- `ready_to_build`
- `under_construction`
- `paused`
- `completed`
- `cancelled`

规则：

- `delivered_inventory_id` 是施工点材料库存，必须使用 `construction_site` 类型的 `InventoryContainer`。
- 材料由物流订单、单位手动搬运或调试入口送入施工点库存。
- 施工只消耗施工点库存，不从仓库、背包或 UI 汇总直接扣除。
- 取消施工时，只返还施工点库存中仍存在的材料；已经消耗为施工进度的材料按施工规则处理。

### 5.7 LogisticsOrder

`LogisticsOrder` 表达一次从具体位置取道具并送到具体位置的搬运请求。采集、施工、生产和火箭装载都可以产生物流需求，但搬运动作本身是独立系统。

字段建议：

- `logistics_order_id`
- `expedition_id`
- `item_id`
- `count`
- `source_location`
- `target_location`
- `assigned_unit_instance_id`
- `state`
- `reserved_item_refs`
- `created_by`
- `failure_reason`

`state`：

- `open`
- `reserved`
- `picked_up`
- `in_transit`
- `delivered`
- `blocked`
- `cancelled`

规则：

- `source_location` 和 `target_location` 必须是 `ItemLocation` 或可解析为 `ItemLocation` 的结构。
- 订单预留后，其他订单不能再预留同一批道具。
- 订单完成时必须生成 `InventoryTransfer` 或地上物状态变化记录。
- 物流订单不能凭空创建或销毁道具。

### 5.8 DropPlan

`DropPlan` 表达一次空投准备结果，是运行状态和存档数据，不是 Resource 定义。

字段建议：

- `drop_plan_id`
- `drop_pod_id`
- `target_coordinate`
- `seed`
- `selected_awakened_unit_instance_ids`
- `selected_unit_platform_items`
- `selected_stack_items`
- `selected_item_instance_ids`
- `weight_limit`
- `used_weight`
- `created_from_orbit_state_id`

规则：

- 觉醒者引用既有 `unit_instance_id`，进入远征前从轨道可用列表锁定。
- `selected_unit_platform_items` 使用 `{ item_id, count, target_unit_id }` 结构；`item_id` 指向 `unit_platform` 类道具，`target_unit_id` 指向将生成的 `UnitData`。
- 量产机优先由 `unit_platform` 道具消耗后生成 `UnitInstance`。
- 可堆叠物资使用 `item_id/count`。
- 装备、芯片、工具和改装件实例使用 `item_instance_id`。
- 空投舱不允许超载，超过 `DropPodData.weight_limit` 时不能创建正式远征。
- `DropPlan` 由 `GameSession` 持有当前计划 ID，并在存档顶层 `drop_plans` 实例池保存。

## 6. 库存系统

### 6.1 库存层级

库存容器包括：

- `unit_inventory`：单位携带库存。
- `surface_storage`：地表仓库库存。
- `building_input`：建筑输入库存。
- `building_output`：建筑输出库存。
- `construction_site`：施工点材料库存。
- `rocket_cargo`：火箭货舱库存。
- `orbit_inventory`：轨道永久库存。
- `trade_buffer`：交易确认前的临时库存。
- `drop_pod_cargo`：空投携带库存。

每个库存容器都使用统一结构，区别只在容量、允许物品类型、所有者和生命周期。

### 6.2 InventoryContainer

字段建议：

- `inventory_id`
- `owner_type`
- `owner_id`
- `slot_limit`
- `weight_limit`
- `accepted_tags`
- `blocked_tags`
- `item_stacks`
- `item_instance_ids`

容量规则：

- 可按格位限制。
- 可按重量限制。
- 可同时使用格位和重量。
- 火箭货舱、空投舱必须至少使用重量限制。
- 仓库可优先使用格位和容量限制。
- 空投舱重量限制是硬限制；火箭货舱允许标记超载，后续第 10 步按超载重量计算燃料消耗。

### 6.3 库存操作

基础操作：

- 添加道具。
- 移除道具。
- 查询数量。
- 查询重量。
- 容量检查。
- 库存间转移。
- 查询道具位置。
- 拆分堆叠。
- 合并堆叠。
- 保留或锁定关键物品。
- 记录库存转移批次。

库存转移必须返回明确结果：

- 成功。
- 道具不存在。
- 数量不足。
- 目标容量不足。
- 目标不接受该道具类型。
- 道具被锁定。
- 数据定义缺失。

这些失败结果要用于 UI 提示和日志，不能只静默失败。

禁止操作：

- 从“地表总量”“当前可用量”“仓库汇总”这类派生数字直接扣除道具。
- 在没有 source 和 target 的情况下修改道具数量。
- 生产建筑跨过输入库存，直接从仓库或单位背包消耗材料。
- 施工点跨过物流，把材料从任意库存瞬间转成施工进度。

库存转移记录建议字段：

- `transfer_id`
- `from_inventory_id`
- `to_inventory_id`
- `item_id`
- `count`
- `item_instance_ids`
- `reason`
- `expedition_id`
- `related_run_record_id`

普通堆叠物资可以在转移记录中追踪来源，不要求每个堆叠长期持有独立 ID。

转移记录持久化规则：

- 普通 UI 整理产生的短期转移记录可以只进入运行日志。
- 与空投创建、火箭装载、回归结算相关的转移记录必须持久化到存档顶层 `inventory_transfers`。
- 回归结算创建 `RunRecord` 时，必须把相关 `transfer_id` 写入轮次记录，保证读档后仍能审计结算链路。

### 6.4 重量和载重

重量计算统一来自 `ItemData.unit_weight`。

计算规则：

```text
堆叠重量 = unit_weight * count
实例重量 = ItemData.unit_weight + 实例修正
库存总重量 = 所有堆叠重量 + 所有实例重量
```

火箭和空投舱使用总重量进行限制。空投舱不允许超载；火箭货舱允许超载但必须记录超载状态，后续火箭超载燃料消耗也基于同一重量统计。

## 7. 轨道永久层数据

`OrbitState` 是多轮远征之间保留的核心状态。

字段建议：

- `orbit_state_id`
- `save_version`
- `inventory_id`
- `credits`
- `unlocked_blueprint_ids`
- `unlocked_protocol_ids`
- `awakened_unit_instance_ids`
- `available_mass_unit_instance_ids`
- `known_coordinates`
- `story_flags`
- `completed_run_record_ids`

轨道层负责保存：

- 带回物资。
- 带回装备、芯片、工具、蓝图。
- 觉醒者团队。
- 已制造但尚未投入远征的量产单位实例。
- 已解锁蓝图和协议。
- 已发现坐标。
- 剧情进度。

轨道层不保存当前地表地图细节。当前远征仍在进行时，地表状态属于 `ExpeditionState`。

单位平台和量产机机体数量只来自 `inventory_id` 指向的轨道库存中 `unit_platform` 类道具，不在 `OrbitState` 上另设数量字段，避免破坏统一道具体系。`available_mass_unit_instance_ids` 只保存已经实例化并停放在轨道中的量产单位，不与 `awakened_unit_instance_ids` 重叠。

字段建议：

- `expedition_id`
- `seed`
- `drop_plan_id`

- `active_unit_instance_ids`
- `surface_inventory_ids`

- `building_instance_ids`
- `map_state`
- `rocket_state`
- `discovered_ids`
- `event_state`
- `created_at_run_time`

第二步以后，第一步文档中的 `initial_units` 和 `initial_items` 作为场景 payload 的语义入口保留，正式远征创建以 `DropPlan -> ExpeditionState -> drop_pod_cargo / active_unit_instance_ids` 为准，避免同时维护两套远征入口。

`map_state` 本阶段定义最终接口字段：

## 10. 存档结构

存档需要同时表达永久层和当前远征层。

建议顶层结构：

```text
SaveGame
  save_version
  created_at
  updated_at
  active_scene_id
  game_session
  drop_plans
  item_instances
  unit_instances
  building_instances
  inventories
  inventory_transfers
```

规则：

- `save_version` 必须存在，用于后续兼容迁移。
- `game_session` 是轨道层、当前远征层和轮次记录的权威入口，延续第一步定义的 `GameSession` 边界。
- 顶层 `drop_plans`、`item_instances`、`unit_instances`、`building_instances`、`inventories`、`inventory_transfers` 是实例池或审计记录池，供 `game_session` 内的 ID 引用，不直接形成第二套轨道或远征状态。
- 存档中保存实例状态，不重复保存完整 Resource 定义。
- 存档读取时按 ID 重新关联 Resource 定义。
- 找不到定义数据时要记录错误，并使用可识别的错误对象或缺失资源标记，不直接崩溃。
- 当前没有远征时，`active_expedition` 可以为空。
- 回归结算完成后，`active_expedition` 可以归档或标记完成，但不能直接丢失轮次记录。

## 11. 数据加载和校验

### 11.1 加载顺序

推荐加载顺序：

1. 加载 Resource 定义数据。
2. 校验 ID 唯一性。
3. 加载存档顶层结构。
4. 加载库存和实例数据。
5. 将实例数据关联到 Resource 定义。
6. 校验轨道层、远征层和轮次记录引用。
7. 输出加载报告。

### 11.2 校验规则

必须校验：

- Resource ID 不重复。
- 存档引用的 `item_id`、`unit_id`、`building_id` 存在。
- 库存中数量大于 0。
- 不可堆叠道具不能只以 `ItemStack` 表达。
- 唯一道具不能重复实例化，除非带有明确允许标记。
- 觉醒者实例 ID 不重复。
- `drop_plan_id` 必须存在于存档顶层 `drop_plans`。
- `related_transfer_ids` 必须存在于存档顶层 `inventory_transfers`。
- `selected_unit_platform_items.target_unit_id` 必须存在于 `UnitData`。
- 空投舱重量不能超过限制。
- 火箭货舱超过限制时必须明确标记为超载。
- 轨道库存、地表库存和火箭货舱不会同时拥有同一个 `ItemInstance`。

### 11.3 错误处理

数据错误分级：

- `warning`：不影响启动，但需要日志提示，例如描述缺失、图标缺失。
- `recoverable_error`：可用错误对象或缺失资源标记恢复，例如某个非关键道具定义缺失。
- `fatal_error`：无法安全继续，例如存档版本无法识别、核心角色实例重复、库存所有权循环。

日志前缀：

- `[数据]`
- `[存档]`
- `[库存]`

## 13. 首批正式定义数据和资源

本阶段应提供首批正式定义数据和配套资源，用于验证链路并作为后续系统继续扩展的稳定基础。数值后续可以扩展和平衡，但 ID、分类、资源引用和对象语义必须按最终规则保留。

首批正式数据必须绑定可用资源引用。本阶段要为首批道具、单位、建筑、技能、事件和空投舱生成实际图片资源。图片资源必须表达对象类别、用途和最终识别方向，不能用缺失图标、纯色块或通用占位精灵满足验收。缺失图标和缺失贴图只作为异常兜底，用于暴露未绑定资源的问题。

首批正式定义数据交付清单：

- 基础矿产道具：金属、硅、稀土、能源块、废料。
- 加工产物道具：合金、电子元件、纯净数据。
- 关键物：数据核心。
- 工具：简易扫描器、简易维修工具。
- 武器：简易实弹枪。
- 芯片：通用 AI 芯片。
- 单位：灵巧、服务型量产机、轻型运输无人机、重型运输机器人、碎石。

- 配方：废料回收金属、制造电子元件、制造合金、制造火箭部件。
- 技能：工程、射击、挖矿、控制。

首批正式数据用途：

- 验证 Resource 加载。
- 验证库存添加、移除和转移。
- 验证空投计划能引用单位和物资。

## 15. 验收标准

第二步完成时，应满足：

- 所有基础矿产道具、加工产物道具、AI 芯片、改装件、武器、工具、单位平台都能用 `ItemData` 表达。
- 可堆叠道具和不可堆叠实例道具边界清晰。
- `UnitData` 和 `UnitInstance` 能区分量产机和觉醒者。
- `BuildingData` 和 `BuildingInstance` 能支持后续地表建造与生产。
- `RecipeData` 能表达基础生产转换。
- `InventoryContainer` 能支持单位、仓库、火箭、轨道、空投舱等不同库存层级。
- 库存转移有明确失败原因。
- 重量统计可用于火箭货舱和空投舱。
- `OrbitState` 能表达永久库存、信用点、蓝图、协议、觉醒者和坐标。
- `ExpeditionState` 能表达当前远征种子、空投计划、单位、建筑、库存、地图接口和火箭接口。
- `RunRecord` 能记录带入、带回、损失、发现和遗留摘要。
- 关键空投、火箭装载、回归结算转移记录可持久化，并可被 `RunRecord` 引用。
- 存档顶层结构包含版本字段。
- 存档读取时能校验 ID 引用和库存所有权。
- 数据加载错误有日志和分级处理。
- 道具、单位、建筑、技能、事件和空投舱的首批正式数据都有对应实际图标资源引用。
- 单位和建筑的首批正式数据都有对应实际地表精灵资源引用。
- 缺失图标、缺失贴图和通用占位精灵不能用于满足首批正式数据资源验收。
- 首批正式数据能跑通“轨道库存 -> 空投计划 -> 地表库存 -> 火箭货舱 -> 回归轨道库存”的数据链路。
- 不引入与当前阶段无关的完整交易、战斗、程序生成或 UI 复杂逻辑。
- 不写入本机绝对路径。

## 16. 风险点

需要优先避免的问题：

- 地表矿产、轨道库存、火箭货舱各自定义一套物资字段，导致结算难以维护。
- 显示名被当作逻辑 ID，后续改名破坏存档。
- 所有物品都只做堆叠，导致武器、芯片、改装件、觉醒者绑定状态无法表达。
- 过早把交易、生产、战斗数值写死在脚本中，后续难以调整。
- 存档保存完整 Resource 内容，导致数据更新后兼容困难。
- 库存转移静默失败，UI 和结算无法解释物资变化。
- 觉醒者和量产机使用同一种实例规则，长期成长边界混乱。

处理原则：

- 统一道具定义，分层保存实例状态。
- 存档保存 ID 和实例状态，Resource 定义由项目数据加载。
- 库存容器通用化，但所有权和生命周期显式记录。
- 回归结算只通过火箭货舱和结构化结果写回轨道层。
- 首批正式数据用于验证链路，数值后续可扩展和平衡，但 ID、分类、资源引用和对象语义按最终规则保留。
