# 第六步策划案：地表资源、建造、生产和电力系统

## 1. 目标定位

第六步要把第五步已经建立的 RTS 单位选择和正式指令接口，接入地表临时基地的核心生产体系。玩家需要能在地表远征中采集资源、回收废料、搬运物资、放置建筑、完成施工、使用仓库、执行配方生产，并通过太阳能板、风力发电机和电池组维持设施运行。

本阶段完成后，项目应具备以下能力：

```text
地表远征
-> 读取空投舱初始库存和当前远征单位
-> 发现并操作首批正式资源点
-> 单位执行 gather / haul / build / repair 指令
-> 建造维修站、基础组装机、仓库、发电设施和火箭组装坪
-> 仓库保存地表采集与生产物资
-> 基础组装机执行正式 RecipeData
-> 电力网络计算发电、耗电、储能和停电状态
-> 资源、建筑、生产、电力状态写回 ExpeditionState
```

本阶段不是完整探索、战斗或火箭回归阶段。资源点可以作为首批正式地表对象落地，但战争迷雾、区域生成、废墟奖励和特殊信号由第 7 步接管；自动炮塔、受击、敌对威胁和战斗损坏由第 8 步接管；火箭发射、货舱装载、超载和回归结算由第 10 步接管。

## 2. 系统边界

纳入范围：

- 地表资源点定义和资源点实例。
- `gather` 指令的采集进度、产出和库存写入。
- `haul` 指令的地表库存搬运和仓库写入。
- 建筑目录、建造预览、放置校验和施工进度。
- `build` 指令的材料预检、施工和建筑实例写回。
- `repair` 指令的建筑维修入口和消耗规则。
- 地表仓库库存、建筑库存和空投舱库存之间的转移。
- `RecipeData` 的地表生产执行。
- 电力生产、耗电、储能、电力不足状态和 UI 反馈。
- 本阶段首批正式资源点、建筑、配方、电力状态资源和音效。

不在本阶段完整展开：

- 程序生成完整地图、战争迷雾和扫描揭示。
- 废墟探索奖励、蓝图碎片、特殊信号和隐藏坐标。
- 敌对单位、伤害、弹药、炮塔攻击和战斗 AI。
- 觉醒者熟练度经验增长和改装效果。
- 火箭货舱装载、发射、回归结算和轨道写回。
- 完整环境灾害和随机事件。

这些后续系统可以读取本阶段写下的资源点、建筑、库存、生产和电力接口，但第六步不得用临时敌人、临时废墟奖励、假火箭结算或占位资源来满足阶段验收。

## 3. 开发依赖顺序

本阶段按以下顺序开发：

1. 明确读取 `ExpeditionState`、`drop_pod_cargo`、`UnitInstance`、`BuildingData`、`RecipeData`、`ItemData`、轨道蓝图和协议的入口。
2. 扩展当前远征层数据，加入资源点实例、地表掉落物、建造计划、生产任务和电力网络状态。
3. 建立资源点定义与首批正式资源点实例，允许调试和首批正式坐标直接提供资源点。
4. 接管第五步 `gather` 指令，完成单位采集、产出批次和地表库存写入。
5. 建立地表库存容器规则，明确空投舱货物区、单位背包、仓库和建筑库存的转移边界。
6. 接管第五步 `haul` 指令，完成单位到仓库、资源点到仓库、建筑输入到仓库的基础搬运。
7. 建立建筑目录和放置模式，读取已解锁蓝图、建筑成本、占地和地形限制。
8. 完成建筑材料预检、材料预留、施工进度、施工取消和回滚规则。
9. 接管第五步 `build` 指令，完成单位施工、建筑实例写回和施工状态显示。
10. 接管第五步 `repair` 指令，完成建筑维修的正式入口、消耗和失败提示。
11. 建立生产任务系统，基础组装机读取 `RecipeData` 并消耗输入、产出输出。
12. 建立电力网络，计算发电、耗电、储能、电力不足和建筑运行状态。
13. 完成地表 HUD 的资源栏、建造菜单、建筑详情、生产队列和电力状态反馈。
14. 落地并引用本阶段资源点、建筑、预览、施工、受损、电力和生产反馈资源。
15. 验证正式流程、调试流程、库存事务、生产消耗、状态写回和失败路径。

## 4. 状态入口和写入边界

### 4.1 读取数据

地表资源、建造、生产和电力系统读取：

- `GameSession.ActiveExpedition`：当前远征权威入口。
- `ExpeditionState.expedition_id`、`seed`、`target_coordinate`：资源点和建筑实例归属。
- `ExpeditionState.active_unit_instance_ids`：可执行采集、搬运、施工和维修的单位。
- `ExpeditionState.surface_inventory_ids`：地表库存容器入口。
- `ExpeditionState.building_instance_ids`：当前地表建筑实例。
- `ExpeditionState.map_state.discovered_resource_point_ids`：已发现资源点 ID。
- `drop_pod_cargo_inventory_id`：空投舱初始库存。
- `OrbitState.unlocked_blueprint_ids`：可建造建筑和可执行配方前置。
- `OrbitState.unlocked_protocol_ids`：维修、电力或生产协议前置。
- `ItemData`、`UnitData`、`BuildingData`、`RecipeData`：定义数据。
- 第五步 `UnitCommand`：`gather`、`haul`、`build`、`repair` 指令。

### 4.2 写入数据

本阶段允许写入：

- `ExpeditionState.resource_node_states`：资源点剩余量、采集状态和耗尽状态。
- `ExpeditionState.ground_item_states`：地表掉落物、待搬运物资和来源记录。
- `ExpeditionState.build_plan_states`：待建造、施工中、暂停、取消和完成的建造计划。
- `ExpeditionState.building_instance_ids`：新建成建筑实例。
- `BuildingInstance.construction_progress`、`durability`、`power_state`、`inventory_id`、`active_recipe_id`、`production_progress`。
- `ExpeditionState.production_jobs`：生产队列、输入预留、输出结果和失败原因。
- `ExpeditionState.power_network_states`：发电、耗电、储能和电力不足状态。
- `ExpeditionState.gather_records`：采集结果、目标、转移和失败原因。
- `ExpeditionState.repair_records`：维修消耗、耐久变化、转移和失败原因。
- `InventoryContainer`：单位、空投舱、地表仓库和建筑库存。
- `InventoryTransfer`：采集、搬运、建造消耗、生产输入和生产输出相关转移记录。
- `UnitInstance.current_command`：采集、搬运、施工和维修状态摘要。

本阶段不允许写入：

- 轨道永久库存。
- 轨道蓝图、协议和信用点。
- 回归结算结果和 `RunRecord` 完成记录。
- 火箭货舱装载结果。
- 战斗击杀、敌对掉落和武器伤害。
- 觉醒者熟练度经验和改装结果。

### 4.3 事务规则

跨库存、跨建筑和跨单位的写操作必须先完整预检，再提交。

需要事务式处理的流程：

- 建筑材料预留。
- 建筑取消返还材料。
- 采集产出写入单位背包或地表掉落。
- 搬运物资从源库存到目标库存。
- 生产输入消耗和输出写入。
- 维修消耗和耐久恢复。

预检必须覆盖：

- 道具 ID 存在。
- 数量足够。
- 目标库存容量、格位、重量和标签限制。
- 实例道具所有权不重复。
- 建筑或资源点仍然存在。
- 单位仍属于当前远征且可控。
- 电力状态允许生产或施工继续。

任何一步失败不得半提交；失败要写入明确 `failure_reason`，并在 UI 和日志中可见。

## 5. 远征层数据扩展

### 5.1 ResourceNodeData

`ResourceNodeData` 表达资源点定义，属于可复用定义数据。

字段建议：

- `id`
- `display_name`
- `description`
- `resource_item_id`
- `node_type`
- `base_yield`
- `max_yield`
- `gather_time`
- `required_command_id`
- `required_tool_tags`
- `preferred_unit_tags`
- `depleted_behavior`
- `icon_path`
- `sprite_path`
- `depleted_sprite_path`
- `requires_scan_level`
- `tags`

规则：

- `resource_item_id` 必须指向 `ItemData`。
- 资源点产出进入统一道具体系，不新增独立资源字段。
- `max_yield` 是首批正式数值，可后续平衡，但 ID、资源语义和产出道具必须稳定。
- `requires_scan_level` 可用于第 7 步扫描系统；第六步只处理已发现资源点。

### 5.2 ResourceNodeInstance

`ResourceNodeInstance` 表达当前远征中一个具体资源点。

字段建议：

- `resource_node_instance_id`
- `resource_node_id`
- `expedition_id`
- `position`
- `remaining_yield`
- `is_discovered`
- `is_depleted`
- `reserved_by_unit_instance_id`
- `linked_inventory_id`
- `source_coordinate_id`
- `created_by_seed`

规则：

- `resource_node_instance_id` 写入 `ExpeditionState.resource_node_states`。
- `remaining_yield` 只能通过采集、回收或调试重置改变。
- 资源点耗尽后保留耗尽状态，便于玩家理解收益递减。
- 程序生成完整分布由第 11 步接管；第六步可为首批正式坐标创建可复现资源点，但必须保存种子和实例 ID。

### 5.3 BuildPlanState

`BuildPlanState` 表达一个尚未完成或施工中的建造计划。

字段建议：

- `build_plan_id`
- `building_id`
- `expedition_id`
- `position`
- `rotation`
- `state`
- `reserved_items`
- `assigned_unit_instance_ids`
- `construction_progress`
- `required_work`
- `failure_reason`
- `created_at`

`state`：

- `preview`：玩家正在预览，未写入正式计划。
- `planned`：已确认建造并通过材料预检。
- `material_reserved`：材料已预留。
- `under_construction`：单位正在施工。
- `paused`：缺人、缺电、被阻挡或玩家暂停。
- `completed`：转为 `BuildingInstance`。
- `cancelled`：取消并返还可返还材料。

### 5.4 GroundItemState

`GroundItemState` 表达地表上可见、可搬运、可审计的掉落物或物资堆。它用于单位背包、资源点产出、建筑输出阻塞和搬运系统之间的临时落点，不替代 `InventoryContainer`。

字段建议：

- `ground_item_state_id`
- `expedition_id`
- `item_stack`
- `item_instance_id`
- `position`
- `source_type`
- `source_id`
- `created_by_transfer_id`
- `reserved_by_unit_instance_id`
- `state`
- `failure_reason`

`state`：

- `available`
- `reserved`
- `picked_up`
- `deposited`
- `expired`

规则：

- 可堆叠掉落物使用 `item_stack`，实例道具掉落物使用 `item_instance_id`，两者不能同时为空，也不能同时非空。
- `source_type` 可以是 `resource_node`、`unit_inventory`、`building_output`、`production_overflow`、`debug`。
- `created_by_transfer_id` 记录来源库存转移；没有转移记录的调试掉落物必须标记 `source_type=debug`。
- 被单位认领搬运时写入 `reserved_by_unit_instance_id`，避免多个单位搬同一堆物资。
- 被搬入目标库存后状态改为 `deposited`，不能直接删除，至少保留到本轮远征审计记录完成。

### 5.5 ProductionJob

`ProductionJob` 表达建筑内一个生产任务。

字段建议：

- `production_job_id`
- `building_instance_id`
- `recipe_id`
- `state`
- `input_inventory_id`
- `output_inventory_id`
- `reserved_input_items`
- `progress`
- `required_work`
- `power_required`
- `assigned_unit_instance_id`
- `failure_reason`

`state`：

- `queued`
- `waiting_input`
- `waiting_power`
- `working`
- `output_blocked`
- `completed`
- `cancelled`

### 5.6 PowerNetworkState

`PowerNetworkState` 表达一个连通电力网络。

字段建议：

- `power_network_id`
- `expedition_id`
- `building_instance_ids`
- `power_generation`
- `power_consumption`
- `battery_capacity`
- `stored_power`
- `power_balance`
- `state`
- `last_update_time`

`state`：

- `online`
- `low_power`
- `offline`
- `isolated`
- `overloaded`

第六步可以先按连接范围或全基地同网计算，但必须保留 `power_network_id`，后续才能扩展到输电线路、区域网络或损坏隔离。

### 6.1 采集标签匹配规则

资源点采集资格由 `required_tool_tags` 和 `preferred_unit_tags` 共同决定。

匹配来源：

- 单位内置能力：来自 `UnitData.tags`，例如 `service`、`worker`、`ground_heavy`、`miner`。
- 装备和工具：来自单位装备的 `ItemData.tags`，例如 `tool`、`repair`、`scan`。
- 装备槽能力：来自第五步单位装备槽，例如 `tool_heavy`、`tool_light`，表示该单位能使用对应等级工具。
- 后续正式工具：第 9 步或后续数据可新增 `mining_tool`、`salvage_tool` 等实际工具道具。

匹配规则：

- `preferred_unit_tags` 命中任一项即可获得采集资格倾向和效率加成，但不能单独绕过工具要求。
- `required_tool_tags` 默认按“任一满足”处理：单位内置能力、装备槽能力或装备道具标签命中任一要求即可执行采集。
- `tool` 表示服务型通用工具能力，`tool_heavy` 表示重型工具接口，`mining_tool` 表示后续正式采矿工具标签。
- 金属、硅和废料的首批正式资源点允许服务型单位通过 `tool`、`service` 或 `worker` 等基础能力采集，不强制玩家先制造专用采矿工具。
- 稀土等高阶矿可以在第 7、9 步通过扫描、工具或改装提高效率；第六步首批少量稀土点允许 `ground_heavy` 或 `miner` 单位以低效率采集。
- 若一个资源点未来要求多个必备标签，必须新增 `required_tool_tag_mode=all` 或等价字段，不能隐式改变当前“任一满足”规则。

## 7. 采集系统

### 7.1 采集流程

```text
玩家右键资源点
-> 第五步解析为 target_type=resource_node / command=gather
-> GatherSystem 校验单位、工具、资源点和容量
-> 单位移动到采集点
-> 开始采集进度
-> 从 ResourceNodeInstance.remaining_yield 扣除产量
-> 写入单位库存、目标仓库或地表掉落
-> 生成 GatherRecord，并在发生库存转移时生成 InventoryTransfer
-> 资源点耗尽时更新耗尽状态
```

### 7.2 采集规则

- 只有拥有 `gather` 指令的单位可以采集。
- `UnitData.tags`、装备标签和工具标签影响采集可用性。
- `service_bot` 可采集废料、金属和硅等基础资源。
- `heavy_cargo_spider` 和 `rockbreaker` 对矿脉类资源点有更高倾向。
- `light_cargo_drone` 不执行重型采矿，但可搬运轻量掉落物或侦察资源点。
- 资源点产出优先进入单位库存；单位库存不足时可以写入附近可用仓库；仍不足时生成地表掉落物。
- 资源点耗尽后保留耗尽精灵和状态，不直接删除。

### 7.3 采集记录

建议 `GatherRecord` 字段：

- `gather_record_id`
- `expedition_id`
- `unit_instance_id`
- `resource_node_instance_id`
- `item_id`
- `count`
- `destination_inventory_id`
- `ground_item_state_id`
- `transfer_id`
- `result`
- `failure_reason`

采集记录必须写入 `ExpeditionState.gather_records`。与库存转移相关的采集结果必须生成 `InventoryTransfer` 并写入 `transfer_id`，以便后续火箭装载、回归结算和角色成长系统审计来源。普通调试日志只能作为辅助，不能替代正式 `GatherRecord`。

## 8. 地表库存和搬运

### 8.1 地表库存类型

第六步使用第二步统一 `InventoryContainer`，不新增独立资源字段。

地表库存容器：

- `drop_pod_cargo`：空投带入资源，生命周期属于当前远征。
- `unit_inventory`：单位背包。
- `surface_storage`：仓库库存。
- `building_input`：建筑输入库存，可与建筑实例绑定。
- `building_output`：建筑输出库存，可与建筑实例绑定。
- `ground_item`：地表掉落物状态引用，不作为长期库存容器优先方案。

### 8.2 搬运流程

```text
玩家右键掉落物 / 仓库 / 建筑
-> 第五步解析为 target_type=item_stack / storage / building_friendly
-> HaulSystem 校验单位、源库存、目标库存和容量
-> 单位移动到源位置
-> 从源库存或地表掉落物取出物资
-> 单位移动到目标位置
-> 写入目标库存
-> 生成 InventoryTransfer
```

### 8.3 搬运规则

- 搬运必须通过统一库存转移，不能直接改 UI 计数。
- 源和目标都要完整预检，避免拿起成功、放下失败造成半提交。
- 可堆叠道具按 `ItemStack` 转移。
- 实例道具按 `ItemInstance` 所有权转移。
- 建筑输入库存只能接受配方或建筑功能允许的道具。
- 仓库库存用于地表生产和火箭装载前的中转，但不等于轨道永久库存。
- 地表仓库中的物资只有通过第 10 步火箭货舱和回归结算才能写回轨道。

## 9. 建筑系统

### 9.1 建筑放置流程

```text
玩家打开建造菜单
-> 选择 BuildingData
-> 检查蓝图、资源、地形、占地和阻挡
-> 显示建造预览
-> 玩家确认放置
-> 创建 BuildPlanState
-> 预留或扣除材料
-> 单位执行 build 指令
-> 施工完成后创建 BuildingInstance
```

### 9.2 放置校验

必须校验：

- `building_id` 存在。
- `requires_blueprint_id` 为空，或存在于 `OrbitState.unlocked_blueprint_ids`。
- 建筑占地没有与单位、建筑、资源点和不可通行地形冲突。
- 建筑位置在当前可操作地表范围内。
- 建造消耗道具在地表可用库存中足够。
- 参与施工单位可执行 `build` 指令。
- 调试建筑放置必须带 `debug_enabled`。

第六步不要求战争迷雾完整接入，但正式流程不能允许玩家在未发现、不可见或未载入区域随意放置建筑；第 7 步接入迷雾后继续使用同一校验入口。

### 9.3 施工规则

- 建筑确认后创建 `BuildPlanState`。
- 材料预留优先来自地表仓库，其次来自空投舱货物区和单位背包。
- 施工中建筑显示施工精灵和进度。
- 施工完成后移除 `BuildPlanState` 或标记 `completed`，并创建 `BuildingInstance`。
- 取消建造时返还未消耗材料；已转换为结构损耗的比例必须写在规则里，不隐式吞资源。
- 施工单位离开、能源不足或路径阻挡时，建造进入 `paused`，不丢进度。

- `building_instance_id`
- `building_id`
- `position`

- `durability`
- `construction_progress`
- `power_state`
- `inventory_id`
- `active_recipe_id`
- `production_progress`
- `power_network_id`
- `work_state`
- `damage_state`

`damage_state`：

- `intact`
- `damaged`
- `critical`
- `destroyed`

第六步只实现施工、维修和基础损坏状态显示；战斗造成损坏由第 8 步接入。

## 13. 电力系统

### 13.1 电力更新流程

```text
收集网络内建筑
-> 计算 power_generation
-> 计算 power_consumption
-> 读取 battery_bank 储能
-> 分配电力
-> 更新 BuildingInstance.power_state
-> 更新 ProductionJob 状态
-> 更新 HUD 电力反馈
```

### 13.2 电力规则

- 发电建筑提供 `power_generation`。
- 耗电建筑读取 `power_consumption` 和生产任务 `power_cost`。
- 电池组提供 `battery_capacity` 和 `stored_power`。
- 电力充足时建筑为 `online`。
- 电力不足但可部分运行时建筑为 `low_power`。
- 无电或网络断开时建筑为 `offline`。
- 储能变化必须可追踪，不能只显示 UI 数字。
- 生产进度只能在 `online` 或规则允许的 `low_power` 状态推进。
- 防御建筑耗电接口可保留，但攻击和弹药由第 8 步接管。

## 14. 维修系统

### 14.1 维修目标

第六步的维修系统只处理建筑和设施维修入口；单位维修可以显示入口并使用维修站状态，但完整战斗后维修策略由第 8 步扩展。

可维修对象：

- `building_friendly`
- `unit_friendly`
- `repair_station` 自身以外的受损设施。

### 14.2 维修规则

- 单位必须拥有 `repair` 指令。
- 单位或附近仓库必须有 `repair_tool_basic` 或建筑允许的维修标签。
- 维修消耗 `metal`、`scrap` 或 `energy_cell`，具体按目标类型和损坏程度计算。
- 维修前完整预检材料、电力和目标状态。
- 维修不会超过建筑最大耐久。
- 维修行为生成 `RepairRecord` 和必要的 `InventoryTransfer`。
- `RepairRecord` 必须写入 `ExpeditionState.repair_records`；运行日志不能替代正式维修记录。

建议 `RepairRecord` 字段：

- `repair_record_id`
- `expedition_id`
- `unit_instance_id`
- `target_type`
- `target_id`
- `consumed_items`
- `consumed_transfer_ids`
- `durability_before`
- `durability_after`
- `result`
- `failure_reason`

`consumed_transfer_ids` 必须引用维修材料消耗产生的 `InventoryTransfer`；没有材料消耗的调试维修必须标记调试来源，不能伪装成正式维修。

第八步接管：

- 敌对目标、伤害、受击、炮塔攻击、防御墙阻挡和自动维修策略。

## 19. 验收标准

第六步完成时，应满足：

- 地表资源、建造、生产和电力系统读取当前 `ExpeditionState`，不创建脱离远征的独立状态。
- `drop_pod_cargo`、单位库存、地表仓库和建筑库存都使用统一 `InventoryContainer`。
- 资源点使用 `ResourceNodeData` 和 `ResourceNodeInstance` 表达，首批正式资源点 ID、产出道具、数值和资源引用完整。
- 首批正式资源点表承载 `required_tool_tags`、`preferred_unit_tags`、`requires_scan_level`、`tags` 和 `depleted_behavior`，采集过滤不能只依赖自然语言描述。
- 已发现资源点能被 `gather` 指令采集。
- 采集产出进入单位库存、仓库或地表掉落物，并生成可追踪记录。
- 地表掉落物使用 `GroundItemState` 表达，可保存、恢复、预留、搬运和审计来源。
- `GatherRecord` 必须写入 `ExpeditionState.gather_records`，并关联 `InventoryTransfer` 或 `GroundItemState`。
- 资源点剩余量减少，耗尽后显示耗尽状态。
- `haul` 指令能在掉落物、单位库存、空投舱、仓库和建筑库存之间搬运物资。
- 搬运、建造材料预留、生产输入和输出写入都通过事务式预检，不会半提交。
- 建造菜单能显示首批正式建筑、消耗、前置蓝图、电力和库存信息。
- 建造预览能显示合法和非法放置反馈。
- 建筑放置会校验占地、蓝图、资源、地形和阻挡。
- 建筑施工会消耗或预留正式库存材料，并写入 `BuildPlanState`。
- 施工完成后创建 `BuildingInstance`，并写入 `ExpeditionState.building_instance_ids`。
- 取消建造能按规则返还未消耗材料。
- 建筑详情能显示耐久、施工进度、电力、库存和生产状态。
- 基础组装机能执行首批正式 `RecipeData`。
- 首批建筑表承载 `function_tags`，生产校验按 `RecipeData.required_building_tags` 和建筑 `function_tags` 匹配。
- 基础组装机能生产服务型平台、轻型运输无人机平台和重型运输机器人平台，输出道具与第四步平台道具 ID 一致。
- `rocket_part` 作为 `building_module` 类道具进入统一库存，不能作为建筑脚本内部计数。
- 生产输入、输出、耗电、等待输入、等待电力和输出阻塞状态可见。
- 电力网络能计算发电、耗电、储能、电力不足和断电状态。
- 电力状态会影响生产和维修，不只显示 UI 数字。
- 维修指令能对受损建筑执行材料预检、消耗和耐久恢复。
- `RepairRecord` 必须写入 `ExpeditionState.repair_records`，并关联消耗材料的 `InventoryTransfer`。
- `rocket_pad` 可作为建筑和生产入口建成，但不执行火箭发射或回归结算。
- 第六步新增资源点、建筑、配方、电力状态、建造预览、施工、受损、生产和音效资源已落地并被实际引用。
- 缺失图标、纯色块、通用占位精灵和静音音效不能用于满足本阶段资源验收。
- `dotnet build` 通过。
- 有 `.sln` 时 `dotnet build godotgame1.sln` 通过。
- Godot headless 能加载项目并进入地表远征，验证资源点、建筑和生产脚本可实例化。
- 用调试参数直接进入地表时，能验证采集、搬运、建造、生产、电力和日志输出。
- 不实现战争迷雾、完整程序生成、战斗伤害、角色成长、火箭发射和回归结算的临时逻辑。
- 不写入本机绝对路径。

## 20. 风险点

需要优先避免的问题：

- 地表资源用独立数字字段保存，绕过统一道具体系和库存转移。
- 建造、生产或维修逐项写库存，失败后停在半提交状态。
- 建筑材料从 UI 汇总扣除，而不是从权威库存容器转移。
- 生产配方硬编码在建筑脚本里，破坏 `RecipeData` 数据驱动。
- 电力只做显示，不影响生产、维修和建筑状态。
- 火箭组装坪在第六步提前完成发射或结算，污染第十步边界。
- 把防御墙、炮塔攻击或敌人伤害提前做成临时战斗逻辑。
- 资源文件存在但没有被地表对象、建筑、生产或电力 UI 实际引用。

处理原则：

- 所有资源都进入 `ItemData` 和 `InventoryContainer`。
- 所有跨容器操作先预检，再事务式提交。
- `BuildingData`、`RecipeData` 和 `ResourceNodeData` 负责定义，实例状态写入当前远征层。
- 第六步完成真实采集、建造、生产和电力写回；探索、战斗、成长、火箭结算只保留正式接口。
- UI 汇总只从权威状态派生，不维护第二套资源或电力数据。
