# 第六步策划案：地表矿产、物品物流、建造、生产和电力系统

## 1. 目标定位

第六步要把第五步已经建立的 RTS 单位选择和正式指令接口，接入地表临时基地的核心生产体系。玩家需要能在地表远征中把矿产来源转化为道具，把道具放在明确位置，通过物流订单搬运到仓库、建筑输入槽、施工点和火箭相关建筑，再由建筑输入 / 输出库存完成生产，并通过太阳能板、风力发电机和电池组维持设施运行。

本阶段完成后，项目应具备以下能力：

```text
地表远征
-> 读取空投舱初始库存和当前远征单位
-> 发现并操作首批正式矿产来源
-> gather 把矿产来源转化为单位背包或地上道具
-> LogisticsOrder 把道具从具体位置搬到具体位置
-> 建造放置生成 ConstructionSiteState 和施工点库存
-> 物流把材料送入施工点，材料满足后单位施工
-> 生产建筑从输入库存消耗，只向输出库存产出
-> 电力网络计算发电、耗电、储能和停电状态
-> 矿产来源、道具位置、物流订单、施工点、建筑、生产、电力状态写回 ExpeditionState
```

本阶段的硬性模型：

- 矿产来源只产出道具，不保存玩家资产。
- 道具必须位于地上、单位背包、空投舱、仓库、建筑输入、建筑输出、施工点、火箭货舱或轨道库存之一。
- 物流订单只表达“从具体位置取道具，送到具体位置”。
- 施工点拥有自己的材料库存；建筑不是确认放置时瞬间扣材料。
- 生产建筑只从输入库存消耗，只向输出库存产出。
- UI 只展示位置和流转状态，不展示可扣除的全局数值。

本阶段不是完整探索、战斗或火箭回归阶段。矿产点可以作为首批正式地表对象落地，但战争迷雾、区域生成、废墟奖励和特殊信号由第 7 步接管；自动炮塔、受击、敌对威胁和战斗损坏由第 8 步接管；火箭发射、货舱装载、超载和回归结算由第 10 步接管。

## 2. 系统边界

纳入范围：

- 地表矿产来源定义和矿产来源实例。
- `gather` 指令的采集进度、产出道具和道具初始位置写入。
- `haul` 指令和 `LogisticsOrder` 的位置到位置搬运。
- 建筑目录、建造预览、放置校验和施工进度。
- 施工点、施工点材料库存、施工材料搬运和 `build` 指令。
- `repair` 指令的建筑维修入口和消耗规则。
- 地上道具、单位背包、空投舱库存、仓库、建筑输入 / 输出库存之间的转移。
- `RecipeData` 的地表生产执行，输入和输出必须经过建筑输入 / 输出库存。
- 电力生产、耗电、储能、电力不足状态和 UI 反馈。
- 本阶段首批正式矿产点、建筑、配方、电力状态资源和音效。

不在本阶段完整展开：

- 程序生成完整地图、战争迷雾和扫描揭示。
- 废墟探索奖励、蓝图碎片、特殊信号和隐藏坐标。
- 敌对单位、伤害、弹药、炮塔攻击和战斗 AI。
- 觉醒者熟练度经验增长和改装效果。
- 火箭货舱装载、发射、回归结算和轨道写回。
- 完整环境灾害和随机事件。

这些后续系统可以读取本阶段写下的矿产点、建筑、库存、生产和电力接口，但第六步不得用临时敌人、临时废墟奖励、假火箭结算或占位数据来满足阶段验收。

## 3. 开发依赖顺序

本阶段按以下顺序开发：

1. 明确读取 `ExpeditionState`、`drop_pod_cargo`、`UnitInstance`、`BuildingData`、`RecipeData`、`ItemData`、轨道蓝图和协议的入口。
2. 扩展当前远征层数据，加入矿产来源实例、地表掉落物、物流订单、施工点、生产任务和电力网络状态。
3. 建立矿产来源定义与首批正式矿产来源实例，允许调试和首批正式坐标直接提供矿产来源。
4. 接管第五步 `gather` 指令，完成单位采集、产出道具和初始位置写入。
5. 建立道具位置规则，明确地上、单位背包、空投舱、仓库、建筑输入、建筑输出、施工点、火箭货舱和轨道库存的边界。
6. 接管第五步 `haul` 指令，建立 `LogisticsOrder`，完成从具体位置到具体位置的搬运。
7. 建立建筑目录和放置模式，读取已解锁蓝图、建筑成本、占地和地形限制。
8. 建筑确认放置后创建 `ConstructionSiteState`，并为施工点创建材料库存。
9. 用物流订单把材料送入施工点，材料满足后接管第五步 `build` 指令完成施工。
10. 施工完成后创建 `BuildingInstance`，并建立建筑输入 / 输出库存。
11. 接管第五步 `repair` 指令，完成建筑维修的正式入口、材料位置和失败提示。
12. 建立生产任务系统，基础组装机读取 `RecipeData`，只从输入库存消耗，只向输出库存产出。
13. 建立电力网络，计算发电、耗电、储能、电力不足和建筑运行状态。
14. 完成地表 HUD 的物流状态、建造菜单、建筑详情、生产队列和电力状态反馈。
15. 落地并引用本阶段矿产点、建筑、预览、施工、受损、电力和生产反馈资源。
16. 验证正式流程、调试流程、位置转移、物流订单、施工点、生产消耗、状态写回和失败路径。

## 4. 状态入口和写入边界

### 4.1 读取数据

地表矿产、物品物流、建造、生产和电力系统读取：

- `GameSession.ActiveExpedition`：当前远征权威入口。
- `ExpeditionState.expedition_id`、`seed`、`target_coordinate`：矿产点和建筑实例归属。
- `ExpeditionState.active_unit_instance_ids`：可执行采集、搬运、施工和维修的单位。
- `ExpeditionState.surface_inventory_ids`：地表库存容器入口。
- `ExpeditionState.building_instance_ids`：当前地表建筑实例。
- `ExpeditionState.map_state.discovered_mineral_deposit_ids`：已发现矿产点 ID。
- `drop_pod_cargo_inventory_id`：空投舱初始库存。
- `OrbitState.unlocked_blueprint_ids`：可建造建筑和可执行配方前置。
- `OrbitState.unlocked_protocol_ids`：维修、电力或生产协议前置。
- `ItemData`、`UnitData`、`BuildingData`、`RecipeData`：定义数据。
- 第五步 `UnitCommand`：`gather`、`haul`、`build`、`repair` 指令。

### 4.2 写入数据

本阶段允许写入：

- `ExpeditionState.mineral_deposit_states`：矿产点剩余量、采集状态和耗尽状态。
- `ExpeditionState.ground_item_states`：地表掉落物、待搬运物资和来源记录。
- `ExpeditionState.construction_site_states`：施工点、材料库存、施工中、暂停、取消和完成状态。
- `ExpeditionState.logistics_order_states`：搬运订单、预留、取货、运输、送达和失败原因。
- `ExpeditionState.building_instance_ids`：新建成建筑实例。
- `BuildingInstance.construction_progress`、`durability`、`power_state`、`input_inventory_id`、`output_inventory_id`、`active_recipe_id`、`production_progress`。
- `ExpeditionState.production_jobs`：生产队列、输入库存、输出库存、输出阻塞和失败原因。
- `ExpeditionState.power_network_states`：发电、耗电、储能和电力不足状态。
- `ExpeditionState.gather_records`：采集结果、目标、转移和失败原因。
- `ExpeditionState.repair_records`：维修消耗、耐久变化、转移和失败原因。
- `InventoryContainer`：单位背包、空投舱、地表仓库、建筑输入、建筑输出和施工点库存。
- `InventoryTransfer`：采集、搬运、建造消耗、生产输入和生产输出相关转移记录。
- `UnitInstance.current_command`：采集、搬运、施工和维修状态摘要。

本阶段不允许写入：

- 轨道永久库存。
- 轨道蓝图、协议和信用点。
- 回归结算结果和 `RunRecord` 完成记录。
- 火箭货舱装载结果。
- 战斗击杀、敌对掉落和武器伤害。
- 觉醒者熟练度经验和改装结果。

### 4.3 事务规则

跨库存、跨建筑和跨单位的写操作必须先完整预检，再提交。

需要事务式处理的流程：

- 施工点材料送达。
- 施工点取消返还材料。
- 采集产出写入单位背包或地表掉落。
- 搬运物资从源位置到目标位置。
- 生产输入消耗和输出写入。
- 维修消耗和耐久恢复。

预检必须覆盖：

- 道具 ID 存在。
- 数量足够。
- 目标位置容量、格位、重量和标签限制。
- 实例道具所有权不重复。
- 建筑或矿产点仍然存在。
- 单位仍属于当前远征且可控。
- 电力状态允许生产或施工继续。

任何一步失败不得半提交；失败要写入明确 `failure_reason`，并在 UI 和日志中可见。

## 5. 远征层数据扩展

### 5.1 MineralDepositData

`MineralDepositData` 表达矿产点定义，属于可复用定义数据。

字段建议：

- `id`
- `display_name`
- `description`
- `yield_item_id`
- `node_type`
- `base_yield`
- `max_yield`
- `gather_time`
- `required_command_id`
- `required_tool_tags`
- `preferred_unit_tags`
- `depleted_behavior`
- `icon_path`
- `sprite_path`
- `depleted_sprite_path`
- `requires_scan_level`
- `tags`

规则：

- `yield_item_id` 必须指向 `ItemData`。
- 矿产点产出进入统一道具体系，不新增独立矿产字段、物资字段或全局资源池。
- `max_yield` 是首批正式数值，可后续平衡，但 ID、矿产语义和产出道具必须稳定。
- `requires_scan_level` 可用于第 7 步扫描系统；第六步只处理已发现矿产点。

### 5.2 MineralDepositInstance

`MineralDepositInstance` 表达当前远征中一个具体矿产点。

字段建议：

- `mineral_deposit_instance_id`
- `mineral_deposit_id`
- `expedition_id`
- `position`
- `remaining_yield`
- `is_discovered`
- `is_depleted`
- `reserved_by_unit_instance_id`
- `linked_inventory_id`
- `source_coordinate_id`
- `created_by_seed`

规则：

- `mineral_deposit_instance_id` 写入 `ExpeditionState.mineral_deposit_states`。
- `remaining_yield` 只能通过采集、回收或调试重置改变。
- 矿产点耗尽后保留耗尽状态，便于玩家理解收益递减。
- 程序生成完整分布由第 11 步接管；第六步可为首批正式坐标创建可复现矿产点，但必须保存种子和实例 ID。

### 5.3 ConstructionSiteState

`ConstructionSiteState` 表达一个尚未完成或施工中的施工点。施工点是建造材料的真实位置，建筑材料必须先被搬运到施工点库存中，不能在确认放置时从汇总数字里扣除。

字段建议：

- `construction_site_id`
- `building_id`
- `expedition_id`
- `position`
- `rotation`
- `state`
- `required_items`
- `delivered_inventory_id`
- `assigned_unit_instance_ids`
- `construction_progress`
- `required_work`
- `failure_reason`
- `created_at`

`state`：

- `planned`：已确认放置，等待物流送材料。
- `waiting_materials`：施工点材料未满足。
- `ready_to_build`：施工点材料满足，可施工。
- `under_construction`：单位正在施工。
- `paused`：缺人、缺电、被阻挡或玩家暂停。
- `completed`：转为 `BuildingInstance`。
- `cancelled`：取消并返还可返还材料。

规则：

- `delivered_inventory_id` 必须指向 `construction_site` 类型库存。
- 建造菜单只创建施工点，不直接消耗仓库、背包或空投舱中的材料。
- 施工进度只能消耗施工点库存中的材料。
- 施工取消时，物流系统根据施工点库存生成返还或搬走订单。

### 5.4 GroundItemState

`GroundItemState` 表达地表上可见、可搬运、可审计的掉落物或物资堆。它用于单位背包、矿产点产出、建筑输出阻塞和搬运系统之间的临时落点，不替代 `InventoryContainer`。

字段建议：

- `ground_item_state_id`
- `expedition_id`
- `item_stack`
- `item_instance_id`
- `position`
- `source_type`
- `source_id`
- `created_by_transfer_id`
- `reserved_by_unit_instance_id`
- `state`
- `failure_reason`

`state`：

- `available`
- `reserved`
- `picked_up`
- `deposited`
- `expired`

规则：

- 可堆叠掉落物使用 `item_stack`，实例道具掉落物使用 `item_instance_id`，两者不能同时为空，也不能同时非空。
- `source_type` 可以是 `mineral_deposit`、`unit_inventory`、`building_output`、`production_overflow`、`debug`。
- `created_by_transfer_id` 记录来源库存转移；没有转移记录的调试掉落物必须标记 `source_type=debug`。
- 被单位认领搬运时写入 `reserved_by_unit_instance_id`，避免多个单位搬同一堆物资。
- 被搬入目标库存后状态改为 `deposited`，不能直接删除，至少保留到本轮远征审计记录完成。

### 5.5 LogisticsOrderState

`LogisticsOrderState` 表达一个位置到位置的搬运请求。它是 `haul` 指令、施工补料、生产补料、建筑输出清空和火箭装载的共同基础。

字段建议：

- `logistics_order_id`
- `expedition_id`
- `item_id`
- `count`
- `source_location`
- `target_location`
- `assigned_unit_instance_id`
- `state`
- `reserved_item_refs`
- `created_by`
- `failure_reason`

`state`：

- `open`
- `reserved`
- `picked_up`
- `in_transit`
- `delivered`
- `blocked`
- `cancelled`

规则：

- `source_location` 和 `target_location` 必须指向地上物、单位背包、空投舱、仓库、建筑输入、建筑输出、施工点或火箭货舱之一。
- 订单只能移动已存在的道具，不能凭空创建道具，也不能把道具送入不存在的位置。
- 订单预留后，源位置对应道具不可被其他订单重复预留。
- 订单完成后必须生成 `InventoryTransfer` 或更新 `GroundItemState`，保证来源可审计。

### 5.6 ProductionJob

`ProductionJob` 表达建筑内一个生产任务。

字段建议：

- `production_job_id`
- `building_instance_id`
- `recipe_id`
- `state`
- `input_inventory_id`
- `output_inventory_id`
- `progress`
- `required_work`
- `power_required`
- `assigned_unit_instance_id`
- `failure_reason`

`state`：

- `queued`
- `waiting_input`
- `waiting_power`
- `working`
- `output_blocked`
- `completed`
- `cancelled`

规则：

- `input_inventory_id` 必须指向当前建筑的输入库存。
- `output_inventory_id` 必须指向当前建筑的输出库存。
- 生产任务启动时从输入库存消耗；产物只能写入输出库存。
- 输出库存满时进入 `output_blocked`，不把产物落到全局汇总。
- 仓库、单位背包和空投舱中的物资必须先通过物流订单送入建筑输入库存，才能被生产消耗。

### 5.7 PowerNetworkState

`PowerNetworkState` 表达一个连通电力网络。

字段建议：

- `power_network_id`
- `expedition_id`
- `building_instance_ids`
- `power_generation`
- `power_consumption`
- `battery_capacity`
- `stored_power`
- `power_balance`
- `state`
- `last_update_time`

`state`：

- `online`
- `low_power`
- `offline`
- `isolated`
- `overloaded`

第六步可以先按连接范围或全基地同网计算，但必须保留 `power_network_id`，后续才能扩展到输电线路、区域网络或损坏隔离。

### 6.1 采集标签匹配规则

矿产点采集资格由 `required_tool_tags` 和 `preferred_unit_tags` 共同决定。

匹配来源：

- 单位内置能力：来自 `UnitData.tags`，例如 `service`、`worker`、`ground_heavy`、`miner`。
- 装备和工具：来自单位装备的 `ItemData.tags`，例如 `tool`、`repair`、`scan`。
- 装备槽能力：来自第五步单位装备槽，例如 `tool_heavy`、`tool_light`，表示该单位能使用对应等级工具。
- 后续正式工具：第 9 步或后续数据可新增 `mining_tool`、`salvage_tool` 等实际工具道具。

匹配规则：

- `preferred_unit_tags` 命中任一项即可获得采集资格倾向和效率加成，但不能单独绕过工具要求。
- `required_tool_tags` 默认按“任一满足”处理：单位内置能力、装备槽能力或装备道具标签命中任一要求即可执行采集。
- `tool` 表示服务型通用工具能力，`tool_heavy` 表示重型工具接口，`mining_tool` 表示后续正式采矿工具标签。
- 金属、硅和废料的首批正式矿产点允许服务型单位通过 `tool`、`service` 或 `worker` 等基础能力采集，不强制玩家先制造专用采矿工具。
- 稀土等高阶矿可以在第 7、9 步通过扫描、工具或改装提高效率；第六步首批少量稀土点允许 `ground_heavy` 或 `miner` 单位以低效率采集。
- 若一个矿产点未来要求多个必备标签，必须新增 `required_tool_tag_mode=all` 或等价字段，不能隐式改变当前“任一满足”规则。

## 7. 采集系统

### 7.1 采集流程

```text
玩家右键矿产点
-> 第五步解析为 target_type=mineral_deposit / command=gather
-> GatherSystem 校验单位、工具、矿产点和容量
-> 单位移动到采集点
-> 开始采集进度
-> 从 MineralDepositInstance.remaining_yield 扣除产量
-> 产出道具写入单位背包；背包不足则形成 GroundItemState
-> 如需入库，由物流订单从单位背包或地上物送往仓库 / 建筑输入
-> 生成 GatherRecord，并在发生库存转移时生成 InventoryTransfer
-> 矿产点耗尽时更新耗尽状态
```

### 7.2 采集规则

- 只有拥有 `gather` 指令的单位可以采集。
- `UnitData.tags`、装备标签和工具标签影响采集可用性。
- `service_bot` 可采集废料、金属和硅等基础矿产。
- `heavy_cargo_spider` 和 `rockbreaker` 对矿脉类矿产点有更高倾向。
- `light_cargo_drone` 不执行重型采矿，但可搬运轻量掉落物或侦察矿产点。
- 矿产点产出优先进入采集单位背包；单位背包不足时生成地表掉落物。
- 采集本身不直接把道具写入仓库、建筑输入或全局汇总；这些转移必须由物流订单完成。
- 矿产点耗尽后保留耗尽精灵和状态，不直接删除。

### 7.3 采集记录

建议 `GatherRecord` 字段：

- `gather_record_id`
- `expedition_id`
- `unit_instance_id`
- `mineral_deposit_instance_id`
- `item_id`
- `count`
- `destination_inventory_id`
- `ground_item_state_id`
- `transfer_id`
- `result`
- `failure_reason`

采集记录必须写入 `ExpeditionState.gather_records`。与库存转移相关的采集结果必须生成 `InventoryTransfer` 并写入 `transfer_id`，以便后续火箭装载、回归结算和角色成长系统审计来源。普通调试日志只能作为辅助，不能替代正式 `GatherRecord`。

## 8. 道具位置和物流

### 8.1 道具位置类型

第六步使用第二步统一 `InventoryContainer`，不新增独立矿产字段、物资字段或全局资源池。

本阶段可出现的位置：

- `ground`：地表掉落物或物资堆。
- `drop_pod_cargo`：空投带入物资，生命周期属于当前远征。
- `unit_inventory`：单位背包。
- `surface_storage`：仓库库存。
- `building_input`：建筑输入库存，可与建筑实例绑定。
- `building_output`：建筑输出库存，可与建筑实例绑定。
- `construction_site`：施工点材料库存。

这些位置可以在 UI 中汇总显示，但所有提交行为都必须回到具体位置。

### 8.2 物流订单流程

```text
玩家右键掉落物 / 仓库 / 建筑输入槽 / 建筑输出槽 / 施工点
-> 第五步解析为 target_type=item_location / storage / building_friendly / construction_site
-> LogisticsSystem 创建 LogisticsOrderState
-> 校验单位、source_location、target_location、道具数量和容量
-> 单位移动到源位置
-> 从源位置取出道具并标记 in_transit
-> 单位移动到目标位置
-> 写入目标位置
-> 生成 InventoryTransfer
```

### 8.3 物流规则

- 搬运必须通过 `LogisticsOrderState` 和统一库存转移，不能直接改 UI 计数。
- 源位置和目标位置都要完整预检，避免拿起成功、放下失败造成半提交。
- 可堆叠道具按 `ItemStack` 转移。
- 实例道具按 `ItemInstance` 所有权转移。
- 建筑输入库存只能接受配方或建筑功能允许的道具。
- 建筑输出库存满时，生产进入 `output_blocked`，需要物流订单清空输出。
- 施工点材料不足时，建造进入 `waiting_materials`，需要物流订单补料。
- 仓库库存用于地表生产和火箭装载前的中转，但不等于轨道永久库存。
- 地表仓库中的物资只有通过第 10 步火箭货舱和回归结算才能写回轨道。

## 9. 建筑系统

### 9.1 建筑放置流程

```text
玩家打开建造菜单
-> 选择 BuildingData
-> 检查蓝图、建造消耗道具、地形、占地和阻挡
-> 显示建造预览
-> 玩家确认放置
-> 创建 ConstructionSiteState
-> 创建施工点材料库存 delivered_inventory_id
-> 物流订单把材料送入施工点
-> 施工点材料满足后单位执行 build 指令
-> 施工完成后创建 BuildingInstance
```

### 9.2 放置校验

必须校验：

- `building_id` 存在。
- `requires_blueprint_id` 为空，或存在于 `OrbitState.unlocked_blueprint_ids`。
- 建筑占地没有与单位、建筑、矿产点和不可通行地形冲突。
- 建筑位置在当前可操作地表范围内。
- 建造消耗道具可以从至少一个具体位置经物流送达施工点。
- 参与施工单位可执行 `build` 指令。
- 调试建筑放置必须带 `debug_enabled`。

第六步不要求战争迷雾完整接入，但正式流程不能允许玩家在未发现、不可见或未载入区域随意放置建筑；第 7 步接入迷雾后继续使用同一校验入口。

### 9.3 施工规则

- 建筑确认后创建 `ConstructionSiteState`。
- 材料不在确认放置时扣除；系统只根据具体位置生成物流需求。
- 物流订单可从地表仓库、空投舱货物区或单位背包把材料送入施工点。
- 施工只能读取施工点的 `delivered_inventory_id`。
- 施工中建筑显示施工精灵和进度。
- 施工完成后将 `ConstructionSiteState` 标记 `completed`，并创建 `BuildingInstance`。
- 取消建造时返还未消耗材料；已转换为结构损耗的比例必须写在规则里，不隐式吞道具。
- 施工单位离开、能源不足或路径阻挡时，建造进入 `paused`，不丢进度。

### 9.4 建筑实例状态

`BuildingInstance` 在第二步基础上补充或沿用以下状态：

- `building_instance_id`
- `building_id`
- `position`
- `rotation`
- `durability`
- `construction_progress`
- `power_state`
- `input_inventory_id`
- `output_inventory_id`
- `active_recipe_id`
- `production_progress`
- `power_network_id`
- `work_state`
- `damage_state`

`damage_state`：

- `intact`
- `damaged`
- `critical`
- `destroyed`

第六步只实现施工、维修和基础损坏状态显示；战斗造成损坏由第 8 步接入。

## 13. 电力系统

### 13.1 电力更新流程

```text
收集网络内建筑
-> 计算 power_generation
-> 计算 power_consumption
-> 读取 battery_bank 储能
-> 分配电力
-> 更新 BuildingInstance.power_state
-> 更新 ProductionJob 状态
-> 更新 HUD 电力反馈
```

### 13.2 电力规则

- 发电建筑提供 `power_generation`。
- 耗电建筑读取 `power_consumption` 和生产任务 `power_cost`。
- 电池组提供 `battery_capacity` 和 `stored_power`。
- 电力充足时建筑为 `online`。
- 电力不足但可部分运行时建筑为 `low_power`。
- 无电或网络断开时建筑为 `offline`。
- 储能变化必须可追踪，不能只显示 UI 数字。
- 生产进度只能在 `online` 或规则允许的 `low_power` 状态推进。
- 防御建筑耗电接口可保留，但攻击和弹药由第 8 步接管。

### 13.3 首批电力状态

| ID | 显示名 | 语义 | 前置来源 | UI 资源 |
| --- | --- | --- | --- | --- |
| `power_online` | 供电正常 | 发电和储能满足当前负载。 | 第六步新增正式电力状态 | `assets/ui/surface/power/power_online.svg` |
| `power_low` | 供电不足 | 可部分运行，生产速度降低或等待。 | 第六步新增正式电力状态 | `assets/ui/surface/power/power_low.svg` |
| `power_offline` | 断电 | 建筑无法生产或维修。 | 第六步新增正式电力状态 | `assets/ui/surface/power/power_offline.svg` |

## 14. 维修系统

### 14.1 维修目标

第六步的维修系统只处理建筑和设施维修入口；单位维修可以显示入口并使用维修站状态，但完整战斗后维修策略由第 8 步扩展。

可维修对象：

- `building_friendly`
- `unit_friendly`
- `repair_station` 自身以外的受损设施。

### 14.2 维修规则

- 单位必须拥有 `repair` 指令。
- 单位或附近仓库必须有 `repair_tool_basic` 或建筑允许的维修标签。
- 维修消耗 `metal`、`scrap` 或 `energy_cell`，具体按目标类型和损坏程度计算。
- 维修前完整预检材料、电力和目标状态。
- 维修不会超过建筑最大耐久。
- 维修行为生成 `RepairRecord` 和必要的 `InventoryTransfer`。
- `RepairRecord` 必须写入 `ExpeditionState.repair_records`；运行日志不能替代正式维修记录。

建议 `RepairRecord` 字段：

- `repair_record_id`
- `expedition_id`
- `unit_instance_id`
- `target_type`
- `target_id`
- `consumed_items`
- `consumed_transfer_ids`
- `durability_before`
- `durability_after`
- `result`
- `failure_reason`

`consumed_transfer_ids` 必须引用维修材料消耗产生的 `InventoryTransfer`；没有材料消耗的调试维修必须标记调试来源，不能伪装成正式维修。

## 19. 验收标准

第六步完成时，应满足：

- 地表矿产、物品物流、建造、生产和电力系统读取当前 `ExpeditionState`，不创建脱离远征的独立状态。
- `drop_pod_cargo`、单位背包、地表仓库、建筑输入、建筑输出、施工点库存都使用统一 `InventoryContainer` 或明确 `GroundItemState`。
- 矿产点使用 `MineralDepositData` 和 `MineralDepositInstance` 表达，首批正式矿产点 ID、产出道具、数值和资源引用完整。
- 首批正式矿产点表承载 `required_tool_tags`、`preferred_unit_tags`、`requires_scan_level`、`tags` 和 `depleted_behavior`，采集过滤不能只依赖自然语言描述。
- 已发现矿产点能被 `gather` 指令采集。
- 采集产出进入单位背包或地表掉落物，不直接写入仓库、建筑输入或全局汇总。
- 地表掉落物使用 `GroundItemState` 表达，可保存、恢复、预留、搬运和审计来源。
- `GatherRecord` 必须写入 `ExpeditionState.gather_records`，并关联 `InventoryTransfer` 或 `GroundItemState`。
- 矿产点剩余量减少，耗尽后显示耗尽状态。
- `haul` 指令能创建 `LogisticsOrderState`，在地上物、单位背包、空投舱、仓库、建筑输入、建筑输出和施工点之间搬运物资。
- 物流订单能表达来源位置、目标位置、预留、取货、运输、送达和阻塞原因。
- 搬运、施工点补料、生产输入和输出写入都通过事务式预检，不会半提交。
- 建造菜单能显示首批正式建筑、消耗、前置蓝图、电力和库存信息。
- 建造预览能显示合法和非法放置反馈。
- 建筑放置会校验占地、蓝图、材料可送达位置、地形和阻挡。
- 建筑确认放置只创建 `ConstructionSiteState` 和施工点库存，不瞬间扣材料。
- 施工点材料由物流订单送达；单位施工只消耗施工点库存。
- 施工完成后创建 `BuildingInstance`，并写入 `ExpeditionState.building_instance_ids`。
- 取消建造能按规则返还未消耗材料。
- 建筑详情能显示耐久、施工进度、电力、库存和生产状态。
- 基础组装机能执行首批正式 `RecipeData`。
- 首批建筑表承载 `function_tags`，生产校验按 `RecipeData.required_building_tags` 和建筑 `function_tags` 匹配。
- 生产建筑只能从自身输入库存消耗，只向自身输出库存产出。
- 仓库、单位背包、空投舱或地上物中的材料必须通过物流订单进入建筑输入库存后才能被生产消耗。
- 基础组装机能生产服务型平台、轻型运输无人机平台和重型运输机器人平台，输出道具与第四步平台道具 ID 一致。
- `rocket_part` 作为 `building_module` 类道具进入统一库存，不能作为建筑脚本内部计数。
- 生产输入、输出、耗电、等待输入、等待电力和输出阻塞状态可见。
- 电力网络能计算发电、耗电、储能、电力不足和断电状态。
- 电力状态会影响生产和维修，不只显示 UI 数字。
- 维修指令能对受损建筑执行材料预检、消耗和耐久恢复。
- `RepairRecord` 必须写入 `ExpeditionState.repair_records`，并关联消耗材料的 `InventoryTransfer`。
- `rocket_pad` 可作为建筑和生产入口建成，但不执行火箭发射或回归结算。
- 第六步新增矿产点、建筑、配方、电力状态、建造预览、施工、受损、生产和音效资源已落地并被实际引用。
- 缺失图标、纯色块、通用占位精灵和静音音效不能用于满足本阶段资源验收。
- `dotnet build` 通过。
- 有 `.sln` 时 `dotnet build godotgame1.sln` 通过。
- Godot headless 能加载项目并进入地表远征，验证矿产点、建筑和生产脚本可实例化。
- 用调试参数直接进入地表时，能验证采集、搬运、建造、生产、电力和日志输出。
- 不实现战争迷雾、完整程序生成、战斗伤害、角色成长、火箭发射和回归结算的临时逻辑。
- 不写入本机绝对路径。

## 20. 风险点

需要优先避免的问题：

- 地表矿产或物资用独立数字字段保存，绕过统一道具体系和库存转移。
- 建造、生产或维修逐项写库存，失败后停在半提交状态。
- 建筑材料从 UI 汇总扣除，而不是由物流订单送入施工点。
- 生产建筑从仓库或全局汇总直接扣料，而不是从建筑输入库存消耗。
- 建筑输出绕过输出库存，直接进入仓库或全局汇总。
- 生产配方硬编码在建筑脚本里，破坏 `RecipeData` 数据驱动。
- 电力只做显示，不影响生产、维修和建筑状态。
- 火箭组装坪在第六步提前完成发射或结算，污染第十步边界。
- 把防御墙、炮塔攻击或敌人伤害提前做成临时战斗逻辑。
- 资源文件存在但没有被地表对象、建筑、生产或电力 UI 实际引用。

处理原则：

- 所有矿产、加工产物和可交易物资都进入 `ItemData`，并且位于具体 `InventoryContainer`、`GroundItemState` 或施工点中。
- 所有跨位置操作先预检，再通过物流订单或库存转移事务式提交。
- `BuildingData`、`RecipeData` 和 `MineralDepositData` 负责定义，实例状态写入当前远征层。
- 第六步完成真实采集、建造、生产和电力写回；探索、战斗、成长、火箭结算只保留正式接口。
- UI 只展示道具位置和流转状态，不维护第二套物资或电力数据，不直接扣除材料。
