# 工具与地图资源引入建议

调研日期：2026-05-27

来源文档：

- `docs/Godot资源库调研.md`
- `docs/瓦片地图系统调研.md`

本文是实施索引用的压缩结论。具体接入前仍要回读来源文档和对应阶段策划案。

## 1. 总原则

- 插件和外部工具只能服务验证、编辑器效率、资源管线或局部算法，不能接管项目核心玩法状态。
- 运行时代码默认 C#；GDScript 插件优先作为编辑器工具、参考实现或隔离模块。
- 地图权威状态必须由项目自己的 C# 数据结构和服务持有，不能让 `TileMapLayer.tile_map_data`、Tiled 文件或 WFC 输出成为远征存档的唯一来源。
- 经济权威状态必须继续遵守“具体位置上的道具”模型；库存、矿产点、建筑、施工点、建筑输入 / 输出、火箭货舱和物流订单不能交给通用库存插件改写。
- 任何插件安装都必须单独提交或单独分支试用，并先明确生成文件、缓存、报告、许可证和 CI 输出目录。

## 2. 当前建议

当前项目程序实现进度仍在第 4 步“空投配置与远征创建”之前或附近。现在适合引入验证和诊断能力，不适合引入瓦片地图、库存、存档、RTS 控制或程序生成插件。

### 2.1 建议当前引入

| 项目 | 建议 | 原因 | 接入条件 |
| --- | --- | --- | --- |
| Godot Project Doctor Mini | 建议优先做最小接入 spike。 | 能补充断脚本、断资源、大纹理、重场景、导出准备和 headless / CI 诊断。 | 固定报告输出目录；必要时更新 `.gitignore`；验证 headless 扫描不影响运行时。 |
| C# 测试基础 | 建议先建立纯 C# 测试路径，随后评估 gdUnit4Net。 | 当前大量库存、存档、交易、空投校验适合用纯逻辑测试保护。 | 优先不依赖 Godot runtime；能用命令行运行；与 `dotnet build` 顺序不冲突。 |
| gdUnit4 / gdUnit4Net | 建议做兼容性 spike，不建议立刻全量绑定。 | gdUnit4Net 符合 C# 测试方向，但资源库页标记 Godot 4.5 mono，需要确认 4.6 项目兼容性。 | spike 覆盖一个纯逻辑测试和一个 Godot runtime 场景测试；失败则退回标准 `dotnet test` + Godot headless。 |

## 4. 具体引入标准

### 4.1 Project Doctor Mini

允许当前引入，但必须满足：

- 输出目录固定，例如 `reports/project_doctor/` 或 `artifacts/project_doctor/`。
- 报告是否入库要明确；默认只入库配置，不入库每次扫描结果。
- 能通过命令行或 Godot headless 运行扫描。
- 扫描失败不能替代 `dotnet build` 和 Godot headless 项目加载验证，只作为额外信号。

### 4.2 测试框架

优先顺序：

1. 标准 C# 测试项目或可命令行运行的纯逻辑测试。
2. gdUnit4Net 兼容性 spike。
3. GdUnit4 仅在需要测试 GDScript 插件或 Godot 场景 Runner 明显收益更高时局部使用。

测试接入后，每次玩法逻辑改动至少覆盖：

- 正常路径。
- 失败路径。
- 边界输入。
- 状态回滚或事务一致性。

### 4.3 瓦片地图与寻路

第 5 步开始建立：

- `SurfaceMapState`：地图权威数据。
- `SurfaceMapService`：地形、坐标、建造和生成查询。
- `SurfaceNavigationService`：从地形、建筑、施工点、矿产点和动态阻挡生成 `AStarGrid2D`。
- `SurfaceTilemapView`：把权威状态渲染到多个 `TileMapLayer`。

禁止事项：

- 不用旧 `TileMap`。
- 不把超大地图直接写进单个 `TileMapLayer`。
- 不让 TileMap navigation 直接承担 RTS 多单位寻路。
- 不让 TileSet 自定义数据替代矿产点、建筑、库存、地上物或物流订单实例。

### 4.4 地图生成插件

第 11 步前不安装 WFC、Better Terrain、TileMapDual 或 Tiled importer。第 11 步评估时必须先满足：

- 种子能复现地图和关键内容。
- 火箭链路关键材料可达。
- 矿产、废墟、危险区和特殊信号能按项目规则生成。
- 生成结果能写入项目自己的 `SurfaceMapState` 和对象实例表。
- 插件输出只作为候选地形或局部结构输入，不作为权威存档。

## 5. 实施前检查

每次准备引入工具或插件时，先回答：

1. 它服务哪个阶段和哪条验收标准？
2. 它是否会接管核心道具、库存、远征、单位、地图或存档权威状态？
3. 它是否要求 GDScript runtime 代码、C++ 插件或额外导出模板？
4. 它会生成哪些文件？是否需要 `.gitignore` 或固定输出目录？
5. 它能否按顺序通过 `dotnet build`、`dotnet build godotgame1.sln` 和 Godot headless 加载？
6. 它失败时，项目是否仍能用原生 Godot / C# 路径继续实现？

如果第 2 个问题答案是“会”，默认不引入，除非先重写阶段设计并得到源依据支持。
