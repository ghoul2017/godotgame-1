# 工作编排文档

## 1. 目的

本文把 `docs/常用命令.txt` 中记录的常用工作指令整理成可执行的 PM 编排流程。目标是让后续 Codex 会话能按同一套方式推进策划、实现、审查、交接、提交和同步，减少临时理解偏差。

本文不是新的设计源依据。涉及玩法、阶段范围、UI 入口、术语和验收标准时，仍按以下源依据链判断：

```text
docs/原始设计.txt -> docs/整体策划案.md -> 专项设计文档 -> 分步实现文档 -> 代码
```

## 2. 总控原则

- PM 主会话负责定范围、拆任务、验收和收口，不把子代理当成并行自由开发者。
- 开始修改前必须先判断任务范围、影响文件和验证方式。
- 每次只推进一个明确目标：下一份策划文档、下一项程序实现、一次规则沉淀、一次遗留问题整理或一次提交。
- 旧文档、旧代码和旧资源默认可能漂移；遇到冲突先回到源依据链，不沿用最近实现。
- 子代理运行时主会话完全等待，不在等待期间继续改同一目标。
- 子代理输出要隔离，主会话只读取最终报告、问题清单或最终产物，不把长过程混入主上下文。
- `git push` 只在用户明确发出 push 指令后执行；普通提交不自动推送。

## 3. 通用启动步骤

所有参与本项目工作的 AI，包括 PM 主会话和子代理，启动任务后都必须先执行：

```text
ls docs
```

执行目的：

- 先看到当前 `docs/` 下真实存在的设计、TODO、工具、验证和遗留文档。
- 避免凭记忆或旧上下文引用不存在、已改名或已过期的文档。
- 为后续选择源依据、专项文档和分步实现文档建立当前文件清单。

子代理最终报告中必须说明已执行 `ls docs`；未执行时，PM 主会话不得采纳该子代理结论。

## 4. 常用命令到工作流

### 4.1 读取 `docs/策划案todo.md` 编写下一步策划案，完成后开启子代理审查修改，直到没有问题

适用场景：推进下一份阶段策划或设计文档。

执行流程：

1. 读取 `AGENTS.md`、`docs/策划案todo.md`、`docs/原始设计.txt`、`docs/整体策划案.md`。
2. 找到 `docs/策划案todo.md` 中第一项未完成条目，确认它的阶段范围和上游依赖。
3. 读取已完成的相邻阶段文档，保持结构一致，但不把旧内容当成高于源依据的约束。
4. 编写或重写对应阶段文档。若结构错误，直接重写结构，不做同义词替换式修补。
5. 开启设计审查子代理，检查源依据、阶段范围、术语、入口、验收标准和文件清单。
6. 若审查有阻断项，主会话修正后再次审查，直到无阻断项。
7. 审查通过后，再更新 `docs/策划案todo.md` 的完成状态。
8. 运行文档级验证：`rg` 检索旧词、错误入口、阶段错位词和新规则关键字，并运行 `git diff --check`。

收口标准：

- 新文档能追溯到源依据链。
- 当前阶段只包含本阶段能完成和能验证的内容。
- 未来系统只以接口、锁定状态、调试能力或遗留问题形式出现。
- TODO 状态只在文档完成并审查通过后修改。

### 4.2 提取本次对话经验写入入口文件

适用场景：一次工作中产生了可复用的工具规则、语法陷阱、验证规则或流程约束。

执行流程：

1. 先判断经验是否具备长期复用价值。一次性进展、普通任务摘要和临时想法不写入入口文件。
2. 检查 `AGENTS.md` 是否已有同类规则，避免重复扩写。
3. 只写入入口级规则：项目定位、工作边界、编码规则、验证规则、Git 规则或明确的工具坑。
4. 如果经验只是尚未解决的问题，写入 `docs/遗留问题.md`，不要混入 `AGENTS.md`。
5. 写完后用 `rg` 检查新规则关键字，确认规则位置清晰且没有重复冲突。

收口标准：

- `AGENTS.md` 保持入口规则属性，不变成流水账。
- 规则必须来自本次实际踩坑、用户明确要求或已验证的稳定流程。
- 已吸收入门规则的问题，不应继续作为普通遗留项重复存在。

### 4.3 读取 `docs/程序实现todo.md` 按照策划案实现下一步功能，完成后开启子代理审查修改，直到没有问题

适用场景：按阶段实现程序功能。

执行流程：

1. 读取 `AGENTS.md`、`docs/程序实现todo.md`、`docs/工具与地图资源引入建议.md`。
2. 找到 `docs/程序实现todo.md` 中第一项未完成阶段。
3. 读取对应策划文档、上游已实现阶段文档和相关源依据，确认本次只做当前阶段。
4. 开始改代码前列出影响范围：场景、脚本、资源、数据、测试或调试入口。
5. 按最小可验证单元实现，不顺手扩大到后续阶段。
6. 运行必要验证：

```text
dotnet build
dotnet build godotgame1.sln
tools/run_godot_console.sh --headless --quit
```

7. 如果新增或修改场景路由，用调试参数进入关键场景验证脚本实例化、payload 传递和日志输出。
8. 开启代码审查子代理，检查设计偏差、阶段越界、数据流所有权、UI 入口、命名、失败路径和测试缺口。
9. 有问题则修正、重跑验证、再次审查，直到无阻断项。
10. 实现和验证都通过后，再更新 `docs/程序实现todo.md` 的完成状态。

收口标准：

- 代码符合当前阶段策划文档，不提前实现后续正式流程。
- 不引入全局资源池、确认放置瞬间扣料、UI 扣除全局数值等错误经济模型。
- C# 构建和 Godot headless 加载通过；无法验证时必须先查找工具路径和替代方案。
- 审查无阻断项后才算完成。

### 4.4 提取本次对话经验写入入口文件，遗留问题写入 `docs/遗留问题.md`

适用场景：一次实现结束后需要把经验和未完成问题分流。

执行流程：

1. 将本次结果分成三类：已完成事实、长期规则、真实遗留问题。
2. 已完成事实只在最终回复或提交信息中说明，不写成长期规则。
3. 长期规则写入 `AGENTS.md`，必须短、可执行、可复用。
4. 真实遗留问题写入 `docs/遗留问题.md`，必须包含触发条件、当前影响、建议处理时机和验证方式。
5. 已经解决或已经吸收入口规则的问题，应从 `docs/遗留问题.md` 移除。
6. 用 `rg` 检索相关旧词、问题名和规则关键字，确认分流干净。

收口标准：

- `AGENTS.md` 只保留规则，不记录任务流水。
- `docs/遗留问题.md` 只保留当前仍会影响后续工作的真实问题。
- 遗留问题不能替代当前阶段必须完成的验收项。

### 4.5 全部提交

适用场景：用户明确要求提交所有本地变更。

执行流程：

1. 运行 `git status --short`，确认变更文件。
2. 运行必要验证。代码变更至少执行项目要求的构建和 Godot headless 验证；纯文档变更至少执行 `git diff --check`。
3. 查看 diff，确认只包含本次任务相关内容；若发现用户已有无关变更，不擅自回滚。
4. 按用户要求提交所有本地变更；提交信息使用中文描述。
5. 提交后再次运行 `git status --short`，确认工作树状态。

收口标准：

- 不主动 push。
- 不提交未理解的异常生成文件。
- 若用户要求“全部提交”，可包含本次相关文档、资源、代码和必要元文件，但提交前仍要说明范围。

### 4.6 `git pull`

适用场景：用户明确要求同步远端最新内容，或继续工作前需要先拉取。

执行流程：

1. 运行 `git status --short`，确认是否有本地未提交变更。
2. 若有本地变更，先判断是否会与 pull 冲突；必要时先提交或让用户明确处理方式。
3. 执行 `git pull`。
4. 若出现冲突，只解决与当前任务相关且能确定正确性的冲突；不能确定时停止并说明冲突文件。
5. pull 后检查 `git status --short` 和关键文档是否被远端更新影响。

收口标准：

- 不为 pull 擅自丢弃本地变更。
- 冲突解决后要运行相应验证。

### 4.7 `git push`

适用场景：用户明确要求推送当前分支。

执行流程：

1. 运行 `git status --short`，确认没有未提交的本次工作残留。
2. 运行 `git branch --show-current`，确认当前分支。
3. 必要时运行 `git log --oneline -5`，确认要推送的提交。
4. 执行 `git push`。
5. 推送后确认远端接受结果。

收口标准：

- 只在用户明确要求时 push。
- 不把未验证或未提交的工作伪装成已推送。

## 5. 子代理角色建议

子代理只在主会话已经明确任务边界后启动。每次只激活一个角色。
子代理启动后第一步也必须执行 `ls docs`，并在最终报告中写明结果。

- 设计审查：检查源依据链、阶段范围、术语、入口和验收标准。
- 实现审查：检查代码结构、数据流、状态所有权、失败路径和项目编码规则。
- UI 审查：检查 Godot UI 最小尺寸反馈、图标收口、同帧重建和布局挤压风险。
- 验证审查：检查构建、Godot headless、调试路由、日志和 `rg` 残留扫描是否足够。
- 交接整理：只整理入口规则或遗留问题，不重写已完成实现。

子代理最终报告应包含：

```text
结论：通过 / 有阻断项 / 有非阻断建议
docs 列表检查：已执行 `ls docs` / 未执行
检查范围：
发现问题：
建议修复：
已执行验证：
仍未覆盖风险：
```

## 6. PM 收口清单

每轮工作结束前，主会话至少检查：

- `git status --short`
- `git diff --check`
- 当前任务要求的构建或文档验证
- TODO 状态是否只在完成后更新
- `AGENTS.md` 是否只写长期规则
- `docs/遗留问题.md` 是否只保留真实未解决问题
- 是否存在旧词、错误入口、阶段越界或全局资源池残留

最终回复必须说明：

- 完成了什么
- 改了哪些文件
- 验证跑了什么，结果如何
- 有哪些未覆盖风险或下一步
