# 第四步策划案：空投配置与远征创建

## 1. 目标定位

第四步要完成从轨道站进入地表远征的正式准备流程。玩家在轨道站空投页进入空投配置，选择坐标、空投舱、觉醒者、量产单位平台、装备实例和携带物资，系统检查容量、重量、解锁条件和库存状态，确认后创建 `DropPlan` 与 `ExpeditionState`。

本阶段完成后，项目应具备以下能力：

```text
轨道站空投页
-> 进入空投配置
-> 读取 OrbitState、轨道库存、角色、坐标、蓝图和协议
-> 选择空投舱、坐标、单位和物资
-> 检查容量、重量、库存和前置条件
-> 确认空投
-> 锁定或扣除轨道资产
-> 创建 DropPlan
-> 创建 ExpeditionState
-> 跳转地表远征
```

本阶段不是地表 RTS 玩法阶段，不实现地表单位 AI、矿产采集、地图生成细节和战斗。地表只接收正式远征状态并验证初始单位、初始库存、空投点和随机种子能正确传入。

## 2. 系统边界

纳入范围：

- 轨道站空投页进入空投配置的正式入口。
- 空投配置页面或场景。
- 空投舱选择、坐标选择、携带单位和物资选择。
- 空投容量、重量、单位容量和禁止携带规则。
- 轨道库存扣除、锁定和回滚规则。
- `DropPlan` 创建。
- `ExpeditionState` 创建。
- 远征创建服务和场景 payload。
- 正式入口与调试入口隔离。
- 首批正式空投数据、UI 资源、图标和音效。

不在本阶段展开：

- 地表 RTS 控制。
- 单位寻路、采集、建造和战斗。
- 地表矿产分布和程序生成细节。
- 火箭建造、货舱装载和回归结算。
- 角色成长、装备拖拽和改装树。

这些内容可以读取本阶段输出的 `DropPlan` 和 `ExpeditionState`，但不能在第四步用临时地表逻辑伪装完成。

## 3. 开发依赖顺序

本阶段按以下顺序开发：

1. 明确轨道站空投页到空投配置的导航入口。
2. 建立空投配置布局、输入隔离、携带清单和反馈资源。
3. 定义空投配置运行态 `DropConfigSession`，用于编辑未确认的选择。
4. 读取 `OrbitState`、轨道库存、角色、蓝图、协议和已知坐标。
5. 加载可用 `DropPodData`，根据蓝图和协议过滤可选空投舱。
6. 完成坐标选择。
7. 完成觉醒者和量产单位平台选择。
8. 完成堆叠物资和实例道具选择。
9. 实时计算重量、格位、单位容量和禁止携带状态。
10. 确认空投时执行库存扣除或锁定、生成转移记录。
11. 创建并持久化 `DropPlan`。
12. 创建 `ExpeditionState`、初始单位实例和 `drop_pod_cargo`。
13. 通过结构化 payload 进入地表远征。
14. 验证失败路径、回滚路径、调试入口和正式入口隔离。

## 4. 状态入口和写入边界

### 4.1 读取数据

空投配置读取：

- `OrbitState.inventory_id`：轨道永久库存。
- `OrbitState.awakened_unit_instance_ids`：可选觉醒者。
- `OrbitState.available_mass_unit_instance_ids`：已实例化量产单位。
- 轨道库存中 `unit_platform` 类道具：可生成量产单位的平台。
- `OrbitState.known_coordinates`：已知坐标。
- `OrbitState.unlocked_blueprint_ids`：已解锁蓝图。
- `OrbitState.unlocked_protocol_ids`：已解锁协议。
- `OrbitState.story_flags`：剧情和功能开放状态。
- `DropPodData`：可复用空投舱定义。
- `ItemData`、`UnitData`、`ItemInstance`、`UnitInstance`：道具和单位定义 / 实例。

### 4.2 写入数据

确认空投成功后允许写入：

- `DropPlan`。
- `ExpeditionState`。
- `drop_pod_cargo` 库存容器。
- 新生成的量产 `UnitInstance`。
- 轨道库存扣除或锁定结果。
- 空投相关 `InventoryTransfer`。
- `GameSession.active_expedition`。
- 场景 payload 中的远征创建载荷。

本阶段不允许写入：

- 地表采集结果。
- 地表建筑实例。
- 火箭货舱和回归结算结果。
- 轮次完成记录 `RunRecord`。
- 伪造的蓝图、芯片、数据核心或回归收益。

### 4.3 GameRoot 职责收敛

第 4 步必须保持远征创建职责从 `GameRoot` 中收敛出来。

处理规则：

- `GameRoot` 只负责初始化、路由和接收场景切换请求。
- 正式远征创建由 `DropPlanService` 或 `ExpeditionCreationService` 负责。
- 轨道站空投页只进入空投配置，不直接创建远征。
- 调试入口可以创建调试远征，但必须走独立调试配置，并在 payload 中标记 `debug_enabled`。

## 5. 空投配置运行态

### 5.1 DropConfigSession

`DropConfigSession` 是配置界面的临时编辑状态，不直接进入存档顶层，只有确认后才生成 `DropPlan`。

字段建议：

- `session_id`
- `source_orbit_state_id`
- `selected_coordinate_id`
- `selected_drop_pod_id`
- `selected_awakened_unit_instance_ids`
- `selected_mass_unit_instance_ids`
- `selected_unit_platform_items`
- `selected_stack_items`
- `selected_item_instance_ids`
- `used_weight`
- `weight_limit`
- `used_slots`
- `slot_limit`
- `used_unit_capacity`
- `unit_capacity`
- `validation_errors`
- `validation_warnings`

### 5.2 DropConfigSession 规则

- 玩家修改选择时只更新 `DropConfigSession`，不扣轨道库存。
- `DropConfigSession` 必须能随时重新校验。
- 离开空投配置未确认时，不生成 `DropPlan`。
- 确认空投前必须再次从权威 `OrbitState` 和库存重新读取数据，避免 UI 旧状态造成重复扣除。

## 8. 单位选择

### 8.1 觉醒者选择

觉醒者来自 `OrbitState.awakened_unit_instance_ids`。

选择规则：

- 必须引用已有 `UnitInstance`。
- 觉醒者状态必须为可用。
- 同一觉醒者不能被重复选择。
- 进入远征后从轨道可用列表锁定，直到回归结算或远征恢复逻辑解除。
- 主角“灵巧”在正式远征中默认作为首批可选觉醒者；任何流程强制携带时仍必须写入 `DropPlan`。

### 8.2 量产单位选择

量产单位来源有两种：

- 已实例化量产单位：来自 `OrbitState.available_mass_unit_instance_ids`。
- 单位平台道具：来自轨道库存中 `unit_platform` 类道具。

平台道具结构沿用第二步：

```text
{ item_id, count, target_unit_id }
```

规则：

- `item_id` 必须指向 `unit_platform` 类道具。
- `target_unit_id` 必须存在于 `UnitData`。
- 平台道具确认空投后从轨道库存扣除。
- 第四步可以生成对应的量产 `UnitInstance`，但不实现单位 AI。
- 生成的量产 `UnitInstance` 归属当前 `ExpeditionState.active_unit_instance_ids`。
- 已实例化量产单位使用 `selected_mass_unit_instance_ids` 写入 `DropPlan`，只锁定并带入，不消耗平台道具，不重复生成实例。

## 10. 容量、重量和校验

### 10.1 计算规则

重量继续使用第二步规则：

```text
堆叠重量 = ItemData.unit_weight * count
实例重量 = ItemData.unit_weight + 实例修正
总重量 = 物资重量 + 装备重量 + 单位平台重量 + 觉醒者和已实例化单位的空投重量
```

容量规则：

- `weight_limit`：所有携带内容总重量不能超过空投舱上限。
- `slot_limit`：堆叠格位和实例道具格位不能超过上限。
- `unit_capacity`：觉醒者、量产单位实例和单位平台占用单位容量。
- `accepted_tags` 和 `blocked_tags`：控制可携带类型。

### 10.2 校验错误

必须阻止确认的错误：

- 未选择坐标。
- 未选择空投舱。
- 空投舱未解锁。
- 选择内容超过重量上限。
- 选择内容超过格位上限。
- 选择单位超过单位容量。
- 轨道库存数量不足。
- 选择了不存在的 `ItemData`、`UnitData` 或实例 ID。
- 选择了被锁定、远征中或剧情不可用的觉醒者。
- 选择了空投舱禁止携带的道具。

### 10.3 校验警告

允许确认但需要提示的警告：

- 未携带维修工具。
- 未携带扫描器。
- 未携带基础能源块。
- 未携带量产单位。
- 携带物资偏重，剩余容量很低。

警告不强制阻止玩家，避免形成强制倒计时或强制模板。

## 11. 确认空投和库存处理

### 11.1 确认流程

```text
玩家点击确认空投
-> 重新读取 OrbitState 和库存
-> 校验 DropConfigSession
-> 创建 drop_pod_cargo 库存
-> 转移堆叠物资和实例道具
-> 锁定或迁移觉醒者
-> 消耗单位平台并生成量产 UnitInstance
-> 创建 InventoryTransfer 记录
-> 创建 DropPlan
-> 创建 ExpeditionState
-> 更新 GameSession.active_expedition
-> 进入地表远征
```

### 11.2 扣除和锁定规则

- 堆叠物资：从轨道库存转移到 `drop_pod_cargo`。
- 实例道具：从轨道库存或角色装备状态转移 / 锁定到当前远征。
- 单位平台道具：从轨道库存扣除，并生成远征内量产 `UnitInstance`。
- 已实例化量产单位：从 `available_mass_unit_instance_ids` 锁定到当前远征，并写入 `DropPlan.selected_mass_unit_instance_ids`。
- 觉醒者：从轨道可用状态锁定到当前远征，不销毁实例。

### 11.3 回滚规则

确认过程中任何一步失败必须回滚：

- 已转移的库存退回轨道库存。
- 已生成的临时量产单位删除或标记无效。
- 已锁定的觉醒者解除锁定。
- 不创建 `DropPlan`。
- 不创建 `ExpeditionState`。
- 不跳转地表。
- 输出明确失败原因。

## 12. DropPlan

### 12.1 字段

`DropPlan` 沿用第二步定义，并补充快照字段：

- `drop_plan_id`
- `drop_pod_id`
- `target_coordinate`
- `seed`

## 19. 验收标准

第四步完成时，应满足：

- 轨道站空投页能进入空投配置。
- 空投配置能读取 `OrbitState`、轨道库存、觉醒者、单位平台、坐标、蓝图和协议。
- 可用空投舱由 `DropPodData`、蓝图和协议决定，不新增独立空投舱解锁字段。
- `DropPodData` 能表达 `requires_blueprint_id` 和 `requires_protocol_ids`。
- 坐标必须来自 `OrbitState.known_coordinates`。
- 玩家能选择空投舱、坐标、觉醒者、量产单位平台、物资和实例道具。
- 空投配置的物资列表和装载清单复用统一库存容器 UI，道具格、状态角标和容量条与轨道库存、单位背包、仓库和货舱保持同源。
- 空投配置实时显示重量、格位、单位容量和校验结果。
- 超重、超格、单位容量超限、库存不足、未解锁和禁止携带会阻止确认。
- 警告不会强制阻止确认。
- 确认空投会创建 `drop_pod_cargo`。
- 确认空投会生成并持久化 `DropPlan`。
- 确认空投会创建 `ExpeditionState`。
- 单位平台会扣除并生成量产 `UnitInstance`。
- 已实例化量产单位会锁定并写入 `DropPlan.selected_mass_unit_instance_ids`，不会重复生成。
- 觉醒者会锁定到当前远征，不被销毁或复制。
- 空投相关库存转移会生成 `InventoryTransfer`。
- 任一步失败会回滚库存、单位和锁定状态。
- `GameRoot` 不再承担正式远征创建职责。
- 正式导航不会伪造空投载荷或直接跳地表。
- 调试入口与正式入口隔离，并能标记 `debug_enabled`。
- 地表场景能接收结构化远征 payload，读取远征 ID、种子、坐标、单位和空投库存。
- 首批空投舱、坐标、容量提示、按钮、图标和音效资源已落地并被实际引用。
- 第四步新增或确认的正式 `ItemData` 具备 ID、显示名、分类、重量、堆叠规则、标签、资源引用和 `target_unit_id`。
- 缺失图标、纯色块和通用占位资源不能用于满足本阶段资源验收。
- `dotnet build` 通过。
- 有 `.sln` 时 `dotnet build godotgame1.sln` 通过。
- Godot headless 能加载项目并进入空投配置和地表远征接收流程。
- 不实现地表 RTS、地图生成、火箭结算或战斗临时逻辑。
- 不写入本机绝对路径。

## 20. 风险点

需要优先避免的问题：

- 轨道站空投页直接创建远征，导致配置流程和库存扣除不可追踪。
- `GameRoot` 继续承担远征创建，后续空投、库存和角色选择边界失控。
- 空投配置修改 UI 时直接扣库存，取消后难以回滚。
- 平台道具、量产单位实例和觉醒者实例混用，导致重复生成或单位丢失。
- 只创建 `ExpeditionState`，没有 `DropPlan` 和转移记录，后续无法复盘带入物资。
- 调试入口和正式入口混杂，正式流程出现假载荷。
- 空投舱容量改进写成独立字段，破坏第二步和第三步已确定的蓝图 / 协议口径。
- 空投配置重新发明一套装载 UI，导致后续火箭货舱和单位背包无法复用。
- 资源文件存在但没有被空投配置 UI 实际引用。

处理原则：

- 配置态、确认态和远征态分开。
- 所有正式创建都走 `DropPlan -> ExpeditionState`。
- 库存变化必须通过统一库存操作和 `InventoryTransfer`。
- UI 使用统一库存容器组件表达来源和目标，不允许用自由拖拽隐式扣库存。
- 觉醒者锁定，量产平台消耗，实例道具转移。
- 失败必须可回滚，成功必须可追踪。
